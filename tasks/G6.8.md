# G6.8 — A launch that failed is reported as a failure, and no secret is in argv

## Spec

Four issues, one pass over `libexec/tp-pump`. Three of them live in the launch
and startup path and one in the wait-reason derivation; all four are the same
defect wearing different clothes — the pump reports a confident answer it did
not earn. Read #103, #124, #87 and #74 with `gh issue view`; every file:line
below is copied from their evidence and every one of them **moves as soon as you
start editing**. Treat a citation as a starting point for `rg`, never as a
coordinate: find the function by name, then work.

### #103 — `git worktree add` is unchecked, so a failed launch logs a success

`launch_unit` cuts the agent's worktree at roughly `libexec/tp-pump:1512-1518`
and inspects neither arm's status:

```bash
  if [[ ! -d "$wt" ]]; then
    if git -C "$REPO_ROOT" rev-parse --verify "refs/heads/$branch" >/dev/null 2>&1; then
      git -C "$REPO_ROOT" worktree add "$wt" "$branch" >/dev/null
    else
      git -C "$REPO_ROOT" worktree add "$wt" -b "$branch" "$BASE_REF" >/dev/null
    fi
  fi
```

Both call sites put `launch_unit` inside a conditional (`if launch_unit "$p";
then` around `:2469`, `launch_unit "$unit" || lrc=$?` around `:1472`), which
suppresses `set -e` inside the function, so control falls straight through to
the runner hand-off. The pump logs `launched T2 -> tp-agent-feat-t2`, counts the
unit live, prints `tick: launched 1 (live=1/4)` and exits 0 while the agent has
been handed a directory containing nothing but a brief.

After: capture the status of whichever arm ran, keep git's stderr instead of
discarding it to `>/dev/null`, `warn` naming the unit, the worktree path and
git's own message, and `return 1`. The gitignore refusal immediately below
(around `:1522-1531`) is the model already in the file — it warns, names the
deciding cause, and returns non-zero. The unit then stays LAUNCH-able and the
tick reports `launched 0`.

The commonest trigger is the most boring one: `BASE_REF` defaults to `main`
(around `:268`, `BASE_REF="${TASKPUMP_PUMP_BASE:-${TASKPUMP_BASE:-main}}"`) and
nothing pre-flights it, so every repository whose default branch is `master`,
`trunk` or `develop` hits this on its first tick. Add the pre-flight beside the
existing `CLAUDE_DIR`/`IMAGE`/`RUNNER`/`BRIEF_TEMPLATE` prerequisite block
(around `:2879-2887`): `rev-parse --verify` `$BASE_REF`, or `$INTEGRATION_BASE`
when `--integration-trunk` is on, and `die` naming both the key
(`TASKPUMP_BASE` / `TASKPUMP_PUMP_BASE`) and the resolved value. It must fire
before any worktree is touched.

### #124 — `TASKPUMP_STATE_DIR` is never created, so the state file is lost silently

Around `libexec/tp-pump:232`, `STATE_DIR="${TASKPUMP_STATE_DIR:-$REPO_ROOT}"`
takes the value as given, and eight paths derive from it: the hook mark file,
the disk-watchdog log, the trunk lock, the quarantine record, the cap file, the
usage-reset file, the state file and the pump log. `rg -n mkdir libexec/tp-pump`
finds no `mkdir` of it. Point it at `~/.local/state/taskpump` on a fresh host —
the path the docs suggest — and the pump prints a healthy banner, ticks, reports
success, and drops nothing: `write_state` emits a raw unprefixed bash error
(`tp-pump: line 2596: …: No such file or directory`) and the tick still says it
completed, quarantine records vanish so `graduate_trunk` opens a PR that omits
every quarantined phase, and `--detach`'s `setsid` fallback dies instantly
because its log redirect fails while the parent reports a healthy pid.

After: create-or-refuse, immediately after the assignment —
`mkdir -p "$STATE_DIR"` or `die` naming the key and the path. The precedent is
in this codebase already: `libexec/tp-task`'s `TASKPUMP_WORKSPACE_ROOT` refusal
(around `:105-116`). Do the same in `libexec/tp-disk-watchdog` (around `:51`),
so the two readers you own agree. The third reader, `runners/local/runner.sh`
(around `:151`), is **not in this task's files** — see Scope.

Independently, in the same commit, stop the banner advertising a knob it cannot
deliver. The cap-file failure only warns inside an `elif [[ "$JOBS_GIVEN" -eq 1
]]` arm (around `:2937`), so without `--jobs` an unwritable cap file is
completely silent, and `CAP_NOTE` (around `:2962-2964`) still reads
`live via <path>`. Drop the `--jobs` guard so an unwritable cap file always
warns, and make `CAP_NOTE` read `(cap file unwritable; no live retuning)`
whenever `CAP_FILE_STAMPED` is `0`. This half survives the `mkdir` on any
read-only or full filesystem, which is why it is not optional.

### #87 — `GITHUB_TOKEN`'s value is put in argv, twice

TaskPump already knows secrets must not reach an argument vector: #14 closed
that leak inside the container, `runners/claude-docker/runner.sh:288` is a bare
`-e GITHUB_TOKEN` with a comment at `:219-222` saying why, and
`tests/test-tp-pump.sh:827-829` asserts it. The pump breaks its own rule one
layer up.

`build_detach_argv` (around `:2751-2773`) forwards
`DETACH_PASSTHROUGH_NAMES` (around `:2740-2743`, which includes `GITHUB_TOKEN`
and `TASKPUMP_NOTIFY_CMD`) as `DETACH_ARGV+=(--setenv="$name=${!name}")`. The
values then sit in the world-readable `/proc/<pid>/cmdline` of the `systemd-run`
process, are captured permanently by any execve auditor, and are persisted by
systemd as the transient unit's `Environment=` for the whole multi-day run. This
is the success path, not an error branch.

And around `:1601`, inside the `cid=$( env … "$RUNNER" launch )` block, every
single launch passes `GITHUB_TOKEN="${GITHUB_TOKEN:-}" \` as an element of an
`env` argv — for a variable the child inherits anyway, because `:2872-2873`
already does `GITHUB_TOKEN="$(gh auth token …)"; export GITHUB_TOKEN`.

After: the token reaches the child through the environment or through a
mode-0600 file, never through a command line. Either write the forwarded
environment to a 0600 file under `$STATE_DIR` and pass
`-p EnvironmentFile=<path>`, deleting it when the unit is torn down, or keep
`GITHUB_TOKEN` and `TASKPUMP_NOTIFY_CMD` out of the `--setenv` loop entirely and
let the detached child re-mint the token — `detach_and_exit` (around `:2858`)
runs *before* the `gh auth token` line, so the child mints its own. The
`setsid`+`nohup` fallback inherits the environment natively and leaks nothing;
it is the behaviour to match. Delete the `GITHUB_TOKEN=` assignment from the
launch `env` argv. Note that `tests/test-tp-pump.sh:563-566` currently asserts
the string `GITHUB_TOKEN=` is *present* in the pump source — that assertion
flips from "forwarded by value" to "inherited".

### #74 — phase grain waits on a branch that never existed and never names it

`phase_deps_integrated` (around `:1148-1159`) delegates to
`apl_phase_integrated` (`lib/pump-lib.sh` around `:562-565`), which is
`git merge-base --is-ancestor` with stderr discarded — so "no such ref" and "not
an ancestor" are one answer. Adopt TaskPump on a repository where the upstream
phases were finished before the pump ever ran and the frontier phase is held
`WAITING (deps done but not yet integrated into auto/trunk)` forever, a reason
no tick can satisfy, and then `STALL_EXIT_TICKS` later the pump exits 3 with a
*different* account (`no live agents, nothing launchable, nothing resumable`).
Two stories, neither naming the branch that is missing. Task grain already has
the existence check and the argument for it in its own comment (around
`:1178-1197`).

After: this is the **diagnostic** repair only. Test
`rev-parse --verify "refs/heads/$dbranch"` first; when the ref is absent record
the blocker phase and its expected branch (e.g. `DEPS_MISSING_BRANCH["$phase"]`)
and still `return 1` — behaviour and exit codes identical. Use the richer reason
at the wait-reason assignment (around `:2033`), naming the blocker phase, the
branch that does not exist, and the three ways out (create the branch, drop
`--integration-trunk`, use `--grain task`). Carry the same sentence into
`stall_exit`'s `reason` (around `:2534-2549`) so the plan line, the state file's
`paused_reason` and the notification give one account instead of three. In
`lib/pump-lib.sh` add a sibling `apl_branch_exists`; do not change
`apl_phase_integrated`'s contract, which is used elsewhere and should keep
answering exactly one question.

Two pins. The reason must still contain the substring `not yet integrated`, or
`tests/test-tp-pump.sh:725`, `docs/CLI-PUMP.md:372` and `:685` are updated in
the same commit — dropping that substring is what makes this stop being
PATCH-safe. And do **not** give phase grain the missing-branch escape hatch task
grain has: that changes when a phase launches, and it is tracked as its own
v0.3.0 issue.

## Scope

You may edit exactly the seven paths in this task's `files:` list. Nothing in
the tool enforces that list — the scheduler dispatched a sibling beside you on
the strength of it, so widening your footprint is how two agents land on one
file in one tick.

Specifically:

- **`runners/local/runner.sh` is not yours.** It is the third reader of
  `TASKPUMP_STATE_DIR` and #124 asks for the same create-or-refuse there, but
  the file belongs to G6.7. Record it in your completion note as debt with the
  exact change wanted; do not edit it.
- **`docs/CONFIG.md` is not yours.** #103 wants a `TASKPUMP_BASE` row saying the
  default is `main` and is verified at startup; #124 wants one sentence next to
  `TASKPUMP_STATE_DIR` saying the directory is created if missing and the run
  refuses if it cannot be. G6.13 owns `docs/CONFIG.md` for this phase — record
  both as debt in your completion note, worded so G6.13 can paste them.
- **`runners/claude-docker/entrypoint.sh` is not yours** (G6.3 and G6.6).
- **Do not touch the argument parser or the brief renderer.** #73, #132, #133,
  #98, #100 and #134 all live in `libexec/tp-pump` and are owned by **G6.9**,
  which is dispatched immediately after you and rebases onto your work. If you
  fix a flag guard "while you are in there", G6.9 lands on top of it.
- `CHANGELOG.md` and `VERSION` belong to G6.13 alone. Write your changelog
  material into your completion note instead.

`runners/claude-docker/runner.sh` is in scope only for the token hand-off — it
is the file that shows the correct shape (`-e GITHUB_TOKEN`) and is where any
receiving-side change for #87 lands.
