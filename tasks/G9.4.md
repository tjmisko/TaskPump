# G9.4 — One extension key and one container runtime, honoured by every reader

## Spec

Two issues — #120 and #116 — that share a shape: a documented key is honoured by
some tools and not others, and the tool that ignores it is the one the operator
looks at to find out whether anything is wrong. Both produce a **confident empty
answer** about a system that is running.

File:line citations come from the issue text. **Line numbers move**; grep for the
identifier named beside each one. G9.3 has just rewritten part of
`libexec/tp-task`'s config block — read that file at HEAD, not from the issue.

### #120 — `tp task` hardcodes `.md` while every reader honours `TASKPUMP_TASK_EXT`

Every *reader* honours the key: `libexec/tp-monitor:158` and `:265`
(`task_file()`), `:922` (`dag_env` forwards it), `libexec/tp-dag-render:83` and
`:130` (`files=("$TASKS_DIR"/*"$TASK_EXT")`), and
`runners/claude-docker/entrypoint.sh:134-135`. The *writer* does not:
`rg -n TASK_EXT libexec/tp-task` returns nothing.

So setting the key does not rename anything — it desynchronises the two halves of
the ledger. `tp task create` keeps writing `<id>.md` and `tp task list` keeps
finding it, while `tp dag-render` scans for the configured extension and prints
`(no tasks found)` over a populated tasks directory and `tp monitor` shows an
empty board. The writer and its own reader agree with each other and disagree
with everything else.

The literals in `libexec/tp-task`: the path builds at `:244` and `:2965`, the
enumeration at `:510` (`-name '*.md'`), the four stem strips
`basename "$f" .md` at `:1601`, `:2373`, `:2613`, `:2671`, the review-task paths
at `:1646` and `:1650`, and fsck's "README.md is not a task" guard at `:2224`.

Route them through **two helpers**, not ten separate edits — one helper each way
is what stops the literal reappearing in the next change:

- `task_path <id>` → `printf '%s/%s%s' "$TASKPUMP_TASKS_DIR" "$id" "$TASKPUMP_TASK_EXT"`,
  replacing the path builds and the review-task paths.
- `task_stem <file>` → `basename "$f" "$TASKPUMP_TASK_EXT"`, replacing the four
  stem strips.

Add `: "${TASKPUMP_TASK_EXT:=.md}"` to the config block beside the tasks-dir
derivation. The enumeration becomes `-name "*$TASKPUMP_TASK_EXT"`. fsck's
non-task guard takes the same key, so a `README.md` in a `.task` ledger stops
being special-cased and a `README.task` starts being flagged.

**Default behaviour must be byte-identical with the key unset** — an existing
`.md` ledger is untouched. That is the assertion that keeps this change safe to
land unattended.

### #116 — `tp monitor` calls `docker` by name

`tp monitor` is the supervisor's dashboard: it is where an operator looks to see
which agents are alive. Three of its container queries invoke the literal binary
`docker` instead of the configured runtime, so on a podman host — or anywhere
`TASKPUMP_DOCKER` points elsewhere — the SESSIONS tab reports no containers, the
"Needs attention" records are empty, the GRAPH tab shows no live branches, and
the Disk gauge silently loses its runtime breakdown, for a fleet that is running
perfectly well. The operator's conclusion from a clean dashboard is that nothing
is running, which is the most dangerous possible misreading of a monitoring tool.

The three sites: `libexec/tp-monitor:789-790` inside `disk_compute` (note the
`command -v` guard itself tests the literal name, so the whole branch is skipped
on a podman-only host); `:983` at the tail of `sessions_compute`; `:1304` in
`graph_live_branches`. The monitor already sources `lib/config.sh` and calls
`tp_load_config` at `:117-120`, but `rg -n 'pump-lib|apl_' libexec/tp-monitor`
returns nothing — it never reaches the shared resolver, `apl_docker`
(`lib/pump-lib.sh:216-218`). Every other tool in the tree goes through it.

What must be true after:

- `libexec/tp-monitor` sources `lib/pump-lib.sh` next to the config core and has
  no command-position literal `docker`.
- `disk_compute` resolves once into a local and guards **the resolved binary**:
  `command -v "$rt"`.
- `graph_live_branches` uses `apl_live_agent_names`.
- `AGENT_PREFIX` comes from `apl_agent_prefix` rather than being re-derived at
  `libexec/tp-monitor:167-168`.
- The remaining `docker` strings in the file (`:853`, `:861`, `fmt_docker_size`,
  the demo line) are display text and a helper name; leave them.

**One deliberate narrowing.** The issue proposes extracting a shared
`apl__runtime_ps_rows` into `lib/pump-lib.sh` for `sessions_compute`'s `-a` plus
`State`/`Status` query. `lib/pump-lib.sh` is **not** in your declared files and is
owned by G9.2, which is co-scheduled with this task. Keep that query local to
`libexec/tp-monitor`, routed through `apl_docker`, and record the extraction as a
named follow-on in your completion note. The same applies to
`runners/claude-docker/runner.sh:120`, which reads only `DOCKER` and not
`TASKPUMP_DOCKER`: that file is not yours — record it for G9.5, which owns the
runners.
