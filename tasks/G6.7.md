# G6.7 — No tool answers when it could not read

## Spec

This is the phase's spine and its largest task. One property connects its three
issues: **a failure inside TaskPump is currently laundered into a different,
wrong, successful-looking answer.** A missing `yq` becomes an empty frontier at
rc 0 — the false-drain shape this project's incident history is about. A missing
`setsid` becomes a pid the operator is told to kill for a process that never
started. A failed `--json` read becomes a phase full of launchable work rendered
as WAITING. And a local-runner agent's `complete` lands in the worktree's
private ledger, so the pump re-dispatches finished work forever.

Issues: **#104** (undeclared hard dependencies), **#135** (the pump discards
every `--json` read's exit status), **#129** (`runners/local` forwards no ledger
dir). Every file:line below is a starting point for a search, not a coordinate.

Blocked on **G6.1** (until the suites pin their state dir, running them from a
worktree rewrites the live supervisor's state — and this task runs them
constantly) and on **G6.2** (which owns `libexec/tp-task` in the previous wave;
take its sanitiser edit as your base).

### #104 — a dependency that is missing must say so

TaskPump probes almost nothing. `rg -n 'command -v (jq|yq|flock|curl|gawk|git)'`
across `bin/ lib/ libexec/ gates/ runners/ hooks/` finds four hits and **none of
them dies**: two are documented `flock` no-op degrades, one classifies host
credentials without deciding, one is a gate cache check. The only dependency
that genuinely dies naming itself is `gawk`, in `libexec/tp-dag-render`. #104's
own body claims `jq`, `flock`, `curl` and `gawk` are probed and die; that claim
is false at HEAD, and #135 records the correction. Fix the behaviour, and note
the corrected premise in your completion note.

- **`yq`.** Every frontmatter read is `yq … 2>/dev/null || echo ""` (around
  `libexec/tp-task:203`, and the same shape at `:238`, `:517`, `:760`, `:762`,
  `:788`, `:826`; the write path is `:214`). With `yq` missing, misnamed, or the
  Python `yq` the README warns against: `tp task list` prints rows of blanks,
  **`tp task ready` prints an empty frontier and exits 0**, `tp task next`
  prints the literal `null`, and `tp task fsck` accuses every task file of
  `frontmatter is not valid YAML` — blaming the ledger for the tool's own
  missing parser.
- **`setsid` in `tp pump --detach`.** When `systemd-run --user` is unavailable
  the pump backgrounds itself with `setsid nohup` (around `tp-pump:3036`), never
  checks the child survived, prints a pid and a `stop: kill <pid>` line, and
  exits 0. On a host without `setsid` nothing is running at all. The systemd arm
  does not check its own status either.
- **`setsid` in `runners/local`.** The runner whose premise is "nothing to
  install" starts the agent with `exec setsid` (around `runners/local/runner.sh:413`)
  and turns its absence into `the agent did not start within 5s` — which points
  the operator at their agent command instead of at the missing tool, every
  tick.

Land `apl_require_tool <binary> <why>` in `lib/pump-lib.sh` beside `apl_docker`:
`command -v` the binary and die naming the tool, the resolved or unresolved
path, and what it is needed for. It must be the **only** spelling of a
dependency probe this change adds, so the message shape is uniform and there is
one place to test. Then: a `TASKPUMP_YQ` indirection routing every `yq` call
site, probed once at `tp-task` startup with a mikefarah flavour check (the same
assertion `.github/workflows/ci.yml` already makes — the check that would make
this bug impossible is already written, it just lives in CI instead of in the
tool); `jq` probed at both tools' startup; `setsid` probed in
`runners/local`'s launch path before starting, with either a documented fallback
or a die naming the package — not a timeout message; and `setsid` probed in the
pump's detach path, with **both** arms verifying before logging success.

Distinguish the two `yq` failures ("no yq at `<path>`" vs "wrong yq — mikefarah's
Go v4 is required, found `<version>`"). Give `fsck`'s parse-failure arm a
distinct message when the parser is absent rather than the file bad, so exit 3
keeps meaning "ledger violations" per `docs/LEDGER-CONTRACT.md` §10.

### #135 — the pump must not answer from a read it did not get

The supervisor asks the ledger seven questions per tick through
`tp task … --json`, and discards the exit status of every one. Each is a
pipeline inside a process substitution or command substitution with `2>/dev/null`
on both halves and nothing inspecting `$?`. Sites at roughly `tp-pump:601`
(`frontier_phases`), `:717` (`phase_lead_task`), `:765` and `:772`
(`load_task_snapshot`), `:1867` (`ledger_status`), `:2066` and `:2079` (the
WAITING-reason snapshot).

A failed read returns *nothing*, and nothing is indistinguishable from "no task
is eligible". The one read that survives is `open_count()`, which goes through
`yq` — so the pump prints its own contradiction out loud: `WAITING (2 open, none
eligible — the ledger lists no open task in this phase — the count and the
listing disagree)`, at rc 0, while `tp task ready --phase T1` prints the
launchable row on the same host. And because `open_count` survives,
`is_drained()` never fires, so the run accumulates stall ticks and exits 3 from
`stall_exit`, paging the operator with `nothing launchable, nothing resumable`
over a ledger that has launchable work — and telling them to read a state file
that `write_state` truncated to zero bytes, because it renders with
`>| "$STATE_FILE" 2>/dev/null || true` and `>|` truncates before `jq` is even
resolved.

Three parts:

- **A.** One checked helper beside the existing readers — a `task_json` that
  captures output and status, dies on non-zero naming the verb and surfacing the
  child's stderr, and never degrades to empty. Route all seven sites through it.
  Process substitution hides the child's status by construction, so those must
  become command substitutions (or use a temp file): that conversion is the
  substantive part of the edit, not the helper.
- **B.** Probe `jq` at startup in both tools so `tp task ready --json` and
  `tp task next` stop dying at **127**, a code §10 never defined and which an
  agent loop reads as either "hard error" or "nothing to do" depending on how it
  tests. Use the code §10 does define for a missing dependency.
- **C.** Make `write_state` atomic: render to a temp file and `mv` into place
  only on success, so a failed render leaves the previous state byte-identical
  instead of destroying it. Keep the failure non-fatal if a failed state write
  must not kill the run — but log it.

### #129 — the local runner must hand the agent the pump's ledger

Every agent launched under `runners/local` writes its task state into the
**worktree's** private `tasks/`, not the ledger the pump reads. `complete`,
`block`, `claim` and `heartbeat` all land in the wrong place, at rc 0, printing
exactly what success looks like. The task stays `in_progress` in the real
ledger, the pump re-dispatches it, and a phase whose work is finished reports as
stalled.

The launch subshell (around `runners/local/runner.sh:402-412`) exports ten
variables and `rg -n 'TASKS_DIR|TASKPUMP_TASKS' runners/local/runner.sh` returns
zero hits. The one ledger variable the pump hands this runner —
`TP_TASKS_DIR`, set at around `tp-pump:1797` — is spelled in a way nothing on
this path reads: `rg -n TP_TASKS_DIR lib/ libexec/` shows nothing in `lib/` or
`libexec/tp-task` consuming it at all. Accidental inheritance does not save it,
because both shipped conf shapes fail: `tp init` writes
`TASKPUMP_TASKS_DIR` **relative** on purpose, and a relative value re-anchors to
the agent's own `$PWD`; the fixture shape has no ledger key at all.

Fix: export the ledger alongside the ten, resolved from the launch inputs the
pump actually sets, under a name `tp task` reads. **The value must be absolute**
— the producer absolutises it today, but a relative value silently re-anchors,
so the runner boundary must `die` on one rather than accept it. Forward
`TASKPUMP_TASK_OUT` and `TASKPUMP_TASK_EXT` for the same reason: the docker
runner's passthrough forwards both and its own header records the lesson that
forwarding one of a pair makes the other silently inert.
