# G9.1 — The pump reads its own gate keys and manufactures no directory the consumer did not ask for

## Spec

Three issues — #119, #123, #109 — that are one pass over `libexec/tp-pump` and
its two immediate neighbours. They are in one task because the edits sit in the
same file and would collide if split; read all three before starting.

Every file:line below comes from the issue text. **Line numbers move.** Treat a
citation as a starting point for a search, never as a coordinate: grep for the
identifier named beside it. Several of these sites have already shifted, and at
least two have already been partly repaired at HEAD (see each section) — verify
the current state of each site before you edit it, and where a code half is
already landed, the remaining work is the assertion and the document that would
have caught it, not a second edit.

### #119 — the two gate keys are literals, and the literal is exported over the operator's value

An operator who sets `TASKPUMP_USAGE_GATE=0` or `TASKPUMP_DISK_GATE=0`, in the
environment or in `taskpump.conf`, gets a run where the gate is still in the
chain, still executes, and — because `export_gate_env` re-exports the pump's own
shell variable — is handed `1` when it looks. The operator's value is not
ignored; it is overwritten on the way out. `TASKPUMP_TOKEN_GATE` is the
counter-example that proves the shape: it is absent from the export block and it
works.

Sites: the assignments the issue cites at `libexec/tp-pump:264-266` (the line
above them, `HEALTH_GATE`, already reads its key), the export block at
`:1040-1043`, and the flags `--no-usage-gate` / `--no-disk-gate` at `:367-368`
which must keep forcing `0` either way. The consumers that read what they are
handed are `gates/claude-usage` (`[[ "${TASKPUMP_USAGE_GATE:-1}" -eq 1 ]]`) and
`apl_disk_low` in `lib/pump-lib.sh`, reached via `gates/disk-low`.

At HEAD the assignments already read their keys
(`USAGE_GATE="${TASKPUMP_USAGE_GATE:-1}"` and its sibling). Confirm that, and
then close the two halves that are not done:

- **The exported value.** Assert with an executable probe gate that a gate
  *process* launched under `TASKPUMP_USAGE_GATE=0` observes `0`. The `gates:`
  chain line alone can be right for the wrong reason, which is why the issue
  names the exported-value assertion as the one that would have caught this.
- **The watchdog-spawn coupling, which must be decided in this task and not
  discovered later.** The disk-watchdog `nohup` spawn is guarded on
  `DISK_GATE`, so honouring the key also makes `TASKPUMP_DISK_GATE=0` suppress
  the watchdog. `docs/PUMP-MECHANISMS.md:329-333` currently states the opposite
  in as many words — that the *flag* suppresses the spawn and the key "does not
  reach this decision at all". Either accept the widened behaviour and rewrite
  that paragraph, or decouple the spawn onto its own condition and document
  that. Do not ship the code with the paragraph as it stands.

### #123 — the quarantine file is written every tick and never read back

When a unit's merge into the integration trunk fails the pump rolls the merge
back, appends the unit to the quarantine file, flips the phase's lead task to
`needs-review` and pages the operator. Nothing reads that file back when
selecting units, so the same red merge is attempted on the next tick, fails the
same way, and re-appends, re-flips and re-pages — every tick, for the life of
the drain. The operator gets a notification storm about one broken merge and a
quarantine file that grows one duplicate line per unit per tick; the graduation
PR body lists the same phase a hundred times.

There are exactly three sites in the tree (`rg -n QUARANTINE_FILE`): the
definition (`libexec/tp-pump:283`), the only write, in `quarantine_unit`
(`:1701-1707`), and the only read, in `graduate_trunk` (`:1817`), which exists
purely to compose the PR body.

What must be true after:

- The file is loaded once per run into a set keyed on field 1 (the unit),
  carrying field 2 (the branch tip SHA recorded at the failure).
- `integrate_one_unit` skips a unit already in the set, with a `dbg_log`, **until
  its branch tip SHA differs from the recorded one**. A human who fixes the
  conflict and pushes gets the retry automatically; a branch nobody has touched
  does not burn a merge attempt per tick.
- `quarantine_unit` is idempotent per `(unit, SHA)`: no duplicate append, no
  repeat `needs-review` flip, no repeat `pump_notify`. This half is worth landing
  even if the skip is not.
- `graduate_trunk`'s PR body lists each quarantined unit once.

**Do not hold the unit back from LAUNCH here.** That is a separate decision and
belongs in `compute_plan` with its own `WAITING` reason string so the plan says
why. Adding it inside the quarantine writer is the wrong place and widens this
task into `compute_plan`, which later phases own.

Existing cases at `tests/test-pump-task-grain.sh:610` and
`tests/test-tp-pump.sh:603`, `:668` touch this path and need review.

### #109 — the hardcoded `ops/` name manufactures a directory and blinds the fs-guard

`ops` is the ledger submodule name of the project TaskPump was extracted from.
It survives as a literal in three places, and the two effects are coupled: the
manufactured `ops/` directory is tolerated today **only** because the
contamination guard's allowlist happens to name `ops` too. Fix either alone and
you get a regression — remove the mount and the allowlist entry is dead; tighten
the allowlist and the manufactured directory starts reporting as contamination
every tick. One commit.

- **The directory.** `OPS_DIR="${TASKPUMP_PUMP_OPS_DIR:-${TASKPUMP_LEDGER_REPO:-$REPO_ROOT/ops}}"`
  at `libexec/tp-pump:139` is handed to the runner as `TP_LEDGER_REPO`, and
  `runners/claude-docker/runner.sh:196-197` defaults it a second time and mounts
  it unconditionally at `:263-268` with no existence check. A container runtime
  creates a missing bind-mount source on the host, so the first agent launch in a
  consumer with no `ops/` manufactures one in the repository root, owned by
  whatever uid the runtime used, where it then shows up in `git status`. Default
  `OPS_DIR` to `REPO_ROOT` — which is exactly what `classify_ops_sync`
  (`libexec/tp-pump:2370-2375`) already treats as the workspace-as-ledger case —
  and have the runner omit the ledger `-v` entirely when `TP_LEDGER_REPO` is
  unset or names a directory that does not exist, saying so.
- **The allowlist.** `APL_FS_GUARD_ALLOWLIST` in `lib/pump-lib.sh:584` is a fixed
  regex naming `ops`, while the ledger is configured through
  `TASKPUMP_LEDGER_REPO` / `TASKPUMP_PUMP_OPS_DIR`. A consumer whose ledger is
  `planning/` gets the guard firing on every legitimate ledger commit; a consumer
  with an unrelated `ops/` source directory gets its source edits silently
  allowlisted — and catching a container that writes the primary tree is the
  guard's entire job. Compose the allowlist at runtime from what the run actually
  resolved: the worktrees dir, the ledger repo when it is inside the workspace,
  the trunk lock and quarantine filenames, and the state files the run writes
  (`STATE_FILE`, `PUMP_LOG`, `CAP_FILE`, `HOOK_MARK_FILE`, `RESET_FILE`, the
  disk-watchdog log, the monitor notes dir) — all of which `tp-pump` already
  computes. `TASKPUMP_FS_GUARD_ALLOWLIST` stays a full override, as
  `docs/GATES.md` describes.
- **A scaffolded consumer must be quiet.** `libexec/tp-init` writes only
  `taskpump.conf` and the tasks directory (`:151-183`) and no ignore lines, so a
  freshly scaffolded consumer sees `FS-GUARD: primary checkout dirty outside
  allowlist` naming the pump's own run files, twice per tick, from its first run.
  Have `tp init` append the run-file ignore lines README's adoption steps already
  prescribe.
- **The header lies.** `hooks/fs-guard:18-20` claims the allowlist covers the
  supervisor's own untracked run files. `docs/GATES.md:499-506` says the opposite
  and is correct; make the header match it.
