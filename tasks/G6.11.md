# G6.11 — A first-time operator has an index, a runbook and adoption steps that leave the tree clean

## Spec

Three documentation issues — #68, #54, #55 — that are one task because they are
one file. All three land in `README.md`, plus one new document and one new
suite. Read them with `gh issue view`. Line citations below come from their
evidence and move as soon as you edit; anchor on the surrounding text, not the
number.

This task is **`README.md`'s owner for phase G6**. Its siblings are recording
README debt in their completion notes instead of editing the file. Before you
start, read the completion notes of every `tasks/G6.*.md` that is already
`done`, and land whatever README material they recorded — in particular
**G6.7's dependency-declaration row**: `yq` (mikefarah's Go v4, not the Python
one), `jq`, `git`, `bash` 4+, GNU `awk`, `flock`, `curl` and `setsid`, stated as
the real dependency set now that the tools probe for them and die naming them
rather than laundering an absence into an empty frontier or a live-looking pid.
Debt recorded by a sibling that finishes *after* you goes to G6.13; say so in
your own completion note so the tail task knows what you did and did not take.

### #68 — the index stops at `docs/`, and there is no runbook

`README.md`'s Documentation table (around `:550-560`) lists exactly the eight
files in `docs/` and stops. Two README-class documents outside that directory
are missing: `templates/README.md`, the contract for the most-customised surface
in the tool — the brief an agent actually reads — and
`runners/claude-docker/README.md`, which carries the image contract, the full
env-name table and the pre-flight hook. Both are reachable only from
mid-paragraph links, so a reader working through the index never learns they
exist. `docs/design/` is named once in passing in the Layout table (around
`:544-545`) and never indexed.

After: three new rows, each in the same "what it answers" framing the existing
rows use — `templates/README.md`, `runners/claude-docker/README.md`, and
`docs/design/` labelled honestly as dated design notes kept as a record rather
than a manual. G6.4 owns the design notes' own banners this phase; write the
`docs/design/` row so it is true whether or not those banners have landed.

Separately there is no runbook. `rg -n -i 'troubleshoot|runbook|recovery'
README.md docs/*.md` finds nothing. The recovery knowledge for the things that
actually go wrong during a drain is all present and all correct and spread
across six documents organised by tool — which is exactly the organisation that
stops working at 02:00, when the operator has a symptom and does not know which
tool owns it.

After: `docs/RUNBOOK.md`, indexed from the same table, organised **by symptom**.
Each entry is one paragraph and a link — never a second copy of an explanation,
because a second copy is a second thing to keep true. #68 lists the symptoms to
cover: the pump exited 3; a task is claimed and nothing is running; the plan
says WAITING and I do not believe it; an agent is alive but hung; the disk
filled or the cap dropped to 0; task state landed in the wrong ledger; FS-GUARD
fires every tick; the monitor shows no sessions. Two more belong there because
G6.7 and G6.8 have just given them diagnostics that did not exist when #68 was
filed, and a diagnostic nobody can find is not a diagnostic:

- **A tool refused at startup naming a missing dependency** (G6.7 / #104) —
  what `yq`, `setsid` and friends are for, and why an absent one now refuses
  instead of printing an empty frontier at exit 0.
- **The pump refused at startup naming `TASKPUMP_BASE`, or logged
  `launched 0` with a worktree warning, or named a blocker branch that does not
  exist** (G6.8 / #103, #124, #74) — the three ways out of the missing-branch
  wait, and the create-or-refuse rule for `TASKPUMP_STATE_DIR`.

Read those two tasks' completion notes for the exact strings the tools now
print, and quote the strings — an operator greps the message they are looking
at.

### #54 — the adoption `.gitignore` block is three entries short

`README.md`'s adopt step 1 (around `:231-245`) says "ignore them the way
TaskPump's own repository does" and hands over an eight-line heredoc. The claim
is false as written. `.next-task` is written into the repo root by
`tp task next` — the very first command the quickstart tells you to run
(`docs/CONFIG.md:368` gives `TASKPUMP_TASK_OUT` a default of
`<parent of the tasks dir>/.next-task`). `.auto-trunk.lock` and
`.auto-trunk-quarantine` land in the repo root on any `--integration-trunk` run,
because `STATE_DIR` defaults to `$REPO_ROOT`. TaskPump's own `.gitignore`
carries all three; the pasted block does not. So an operator who follows the
instructions verbatim has untracked litter in `git status` from step 3 onward,
in a tool whose pitch is that it does not scatter state through your repository.

After: extend the heredoc with the three missing entries and a short inline note
for each, keeping the existing eight lines and their order. Change the lead-in
so it names the reference list and its second half rather than claiming a parity
it does not have: `.gitignore` is the reference list, and it and fs-guard's
allowlist (around `lib/pump-lib.sh:572`) have to agree. **Keep the existing
parenthetical warning about not ignoring `.worktrees/`** — the pump refuses to
launch into a gitignored worktree, and that warning is load-bearing. If the
repository's own `.gitignore` is itself missing a name the tools write into a
consumer's root, fix it there too; that file is yours. `lib/pump-lib.sh` is not
— if the two lists disagree in a way only the allowlist can fix, record it.

Having `tp init` write the block itself is a code change and is deliberately out
of scope.

### #55 — two README claims that send the reader somewhere unhelpful

`README.md:553` advertises "the six supervisor mechanisms" in a document that
says five, twice, and explains why the sixth section is not a mechanism
(`docs/PUMP-MECHANISMS.md:4-7` and `:16-19`; the headings confirm the split —
§1–§5 mechanisms, §6 the resolution rule, §7 the consumer contract). A
re-implementer counting sections finds a resolution rule wearing the wrong label
and either implements it as a mechanism or assumes something is missing.

`README.md:628-630` tells the reader to see `CHANGELOG.md` "for what has moved
and what is still Arachne-shaped" — a to-do list buried inside the frozen 0.1.0
entry whose two bullets have both since shipped (`runner.sh list` exists; a
branch name that cannot round-trip its slug is now rejected at startup).

After: restate the mechanism row to match the document it indexes ("The five
supervisor mechanisms and the incident behind each, plus the resolution rule
they all stand on"), and replace the provenance paragraph with one that keeps
the claim and drops the dead pointer — Arachne remains the reference consumer,
its real configuration is `examples/arachne.conf` annotated pin by pin,
everything TaskPump ships is generic by default, the remaining consumer-shaped
defaults are called out inline in `taskpump.conf.example` and in
`examples/arachne.conf`'s comments, and CHANGELOG records what moved release by
release. **Do not edit the 0.1.0 CHANGELOG entry**: it is a dated record and its
heading was accurate the day it was written. `CHANGELOG.md` is not in your files
in any case.

`docs/PUMP-MECHANISMS.md` is in your footprint so the runbook can link to stable
section anchors and so any sentence there that contradicts a diagnostic G6.7 or
G6.8 just added can be corrected. Do not restate a mechanism in the runbook and
do not renumber sections — the count claim in README depends on that numbering,
and so does the assertion you are about to write.
