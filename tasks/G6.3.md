# G6.3 — No ledger string is reparsed as shell

## Spec

A task file is not trusted input. The ledger repo is bind-mounted read-write
into every agent container, so an agent writes `tasks/<id>.md` on the host
directly; a merged pull request or a push to a shared ledger does the same. Any
tool that builds a shell command *string* out of a value read from that file, or
out of a directory name under the worktrees dir, hands whoever wrote it a shell.
Two of those tools run unattended: `tp agent-watchdog` calls `tp cleanup --stuck`
on a timer, and `tp disk-watchdog` calls `tp cleanup --targets`. The operator
sees "released a stuck task"; what happened is code of the author's choosing,
on the host, as the operator's own user, outside every container and outside the
runner's permission classifier.

Three issues, one discipline: **#95** (a planted `id:` reaches `eval` in
`tp-cleanup`, and no read path validates an id), **#80** (`tp-cleanup` evals
worktree names; the entrypoint interpolates the task id), **#99** (the
entrypoint's session script, in detail). They are one task because after the
sweep they are one remaining edit in one file plus two small guards.

**Read the tree before you edit it.** The sweep landed the largest half of #95
and #80 already, and the issue bodies describe the pre-sweep tree. Every
file:line cited below is a starting point for a search, not a coordinate.

### Already landed — verify, then leave alone

- `libexec/tp-cleanup`'s `act()` is an argv vector with an `act_render` that
  prints a `%q`-quoted, copy-pasteable line under `--dry-run`. The only `eval`
  left in the tool is the deliberate `TASKPUMP_RECLAIM_CMD` evaluation, which is
  an operator-supplied command by design and is documented as such at its site.
- `checked_task_id()` exists in `tp-cleanup`, built on `apl_id_reject_reason`
  and `apl_id_offgrammar_reason` in `lib/pump-lib.sh`, with the deliberate split
  that SAFETY refuses and GRAMMAR only warns.

Confirm both at HEAD. If either has regressed, that is the first thing to fix.

### #99 and #80's PI-D7 — the entrypoint's session script

**This is the live half and the bulk of the task.**
`runners/claude-docker/entrypoint.sh` assembles the entire unprivileged-user
session as one double-quoted script body (`DEV_SESSION_SCRIPT`, around `:634`),
with host-side variables expanded at assignment. `$TASK_ID` is spliced into it
inside single quotes at five sites — around `:667-669` (the `[ -n '$TASK_ID' ]`
test, the `claim`, the `heartbeat --start`) and `:690-697` (`TASK_FILE='$TASKS_DIR/$TASK_ID$TASK_FILE_EXT'`,
the `heartbeat --end`). An id containing a single quote closes the literal and
the remainder runs as shell **as the `dev` user, at bootstrap, before
`claude -p` starts** — that is, before and entirely outside
`--permission-mode auto`, the server-side classifier that is this runner's only
stated safety boundary. `GITHUB_TOKEN` is exported into that script's
environment a few lines above (around `:641`), so the injected code has the live
token in scope. The escalation is classifier bypass and pre-session execution
rather than a new principal, and the file should say so honestly.

The fix: stop interpolating ledger values into the script text at all. The id is
already in the session shell's environment (`TASKPUMP_TASK_ID` is exported
around `:440`), so reference it at run time as a quoted expansion the session
shell resolves — one word no matter what it contains — and export it alongside
`GITHUB_TOKEN` so the reference resolves. Where a value genuinely must be bound
at assembly time, bind it with `printf '%q'`, exactly as the same file already
does for the prompt-part paths and for `TASK_CLI_ARGV`. Apply the same rule
uniformly to `$TASKS_DIR` and `$TASK_FILE_EXT` — they are operator-derived and
lower risk, but the point is that the next value someone adds to that here-doc
is safe by default. Update the comment block above the assignment to state the
new rule, since the current one states the old one.

### #80's remaining guard — worktree names

`libexec/tp-cleanup`'s target sweep globs `"$WORKTREES_DIR"/*/*` (around `:491`)
and the names come from the filesystem. With `act()` now taking words this is no
longer an execution path, but the defence-in-depth guard the issue asks for is
still missing and still worth having: skip, with a named warning naming the
path, any entry whose name contains a character outside `[A-Za-z0-9._/-]`. A
directory nobody could have created by a legitimate branch name is not a
directory to `rm -rf` quietly.

### #95's remaining half — the renderer must agree with the CLI

`lib/dag-layout.awk` captures the frontmatter id verbatim (`cid = unq(substr($0, 4))`,
around `:129`) and `emit_claims`/`emit_index` print it unchanged; `unq()` only
trims quotes and whitespace. So the renderer — which the monitor and
`tp-cleanup`'s claim election both read — still emits ids the CLI would refuse.
Mirror the id check there so the dashboards and the rescue path agree with
`tp-task` about which ids are real: an id failing `TASKPUMP_ID_PATTERN` (or the
safety rule, whichever `lib/pump-lib.sh` distinguishes) is dropped or flagged
consistently with what the CLI does, and the awk must not invent a third
opinion.

### `libexec/tp-agent-watchdog`

It is in this footprint because it is the unattended caller: it pipes
`tp-cleanup --stuck` through `sed` (around `:75`), which discards the child's
exit status. At minimum the watchdog must not report a sweep as successful when
`tp-cleanup` refused a row or exited non-zero. If, on inspection, nothing there
needs to change, **say so explicitly in the completion note** rather than
leaving the reader to guess why the file was declared.
