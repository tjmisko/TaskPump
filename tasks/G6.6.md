# G6.6 — The container refuses to start on credentials it could not strip

## Spec

Four issues, one file pass over the claude-docker runner: **#125** (a failed
credential strip is survivable), **#127** (a false mount-regression warning on
every launch), **#59** (a fallback described as scheduled for deletion that
nothing schedules), **#105** (`TASKPUMP_DOCKER` honoured unevenly across the
runner's verbs). They are one task because they are one edit pass over
`runners/claude-docker/entrypoint.sh` plus its runner, its README and
`docs/RUNNERS.md` — and because three of the four are the same failure mode: the
container telling the operator something that is not true about the shape it is
in.

This task is blocked on **G6.3**, which rewrites the session-script assembly in
the same `entrypoint.sh`. Take G6.3's edit as your base; do not re-litigate the
`$TASK_ID` quoting. Every file:line below is a starting point for a search, not
a coordinate.

### #125 — a failed strip must abort the launch

The runner's strongest credential control is that a container never holds a
rotatable OAuth refresh token. At startup `install_credentials` (around `:319`)
copies the host's agent home wholesale — refresh token and all — and then
*replaces* the credentials file with a stripped, access-token-only copy via
`install_access_only_credentials` (around `:277`). If that replacement fails,
the entrypoint logs one `WARNING` and keeps going. The unstripped host
credentials it just copied stay in the agent's home, get `chown`ed and
`chmod u+rw`ed to the session user, and the agent runs on them for the life of
the container.

That is the exact condition the control exists for. The entrypoint's own comment
says removing the refresh token makes a container PHYSICALLY UNABLE to rotate
it; on this path it is physically able, and because the host mount is read-only
a rotation can never be written back — so the host, and every other client
sharing that token including the operator's own interactive sessions, is logged
out. That is the 2026-06-24 incident recorded in the entrypoint's own header,
re-armed. The refresher cannot rescue it either: on failure it explicitly keeps
the previous copy, and at startup the previous copy **is** the unstripped one.
`docs/RUNNERS.md` §4.1's "or the previous copy is left intact" is true for the
refresher and false for startup.

Fix, preferred form: never place an unstripped file in the agent home at all —
exclude `.credentials.json` from the blanket copy, or remove it before the
transform runs, so a failed transform leaves *no* credentials rather than the
wrong ones. Either way, make a failed startup strip **fatal**: remove the file,
log an ERROR naming the cause, and `exit 75` before the session starts and
before the task heartbeat, so no failed-iteration is recorded against the task.
`exit 75` is already this entrypoint's code for an operator-recoverable startup
failure — the agent-config path fifteen lines below already uses it — so no new
exit-code semantics enter. The refresher's behaviour must not change: a failed
*refresh* still keeps the previous (stripped) copy and does not kill a running
session.

The existing coverage cannot see this: `tests/test-entrypoint.sh` (around
`:251-266`) is two static greps over the entrypoint *source*, and both pass with
the failure branch exactly as shipped. Replace or augment them with a test that
reads the **installed file**, not the source.

### #127 — the mount self-check must know which shape it is in

Every launch in the shape TaskPump itself runs in prints
`WARNING: primary checkout (…) is WRITABLE — read-only mount regression`.
Nothing regressed. When the ledger *is* the code repository
(`TASKPUMP_LEDGER_REPO == TASKPUMP_REPO_ROOT` — TaskPump's own dogfood config
and the README's bring-your-own-repo walkthrough), the runner mounts the
checkout read-write **on purpose**, because the runtime rejects two mounts
naming the same destination. `runner.sh` says so in its own comment and
`docs/RUNNERS.md` §4.3 documents the collapse as deliberate. The self-check
(around `entrypoint.sh:512-523`) simply has no branch for it, and the warning is
emitted from the `touch` probe's **success** path.

The cost is the alarm. The line that would signal a real regression — a
separate-ledger mount set that genuinely collapsed to a blanket read-write
`$REPO_ROOT`, letting an agent edit the primary out from under every other
worktree — is byte-identical to the line every healthy launch prints. It also
reaches the agent, telling it that a hardening its brief asks it to respect has
"regressed", which is exactly the self-contradiction that entitles an agent to
distrust the rest of the brief.

Branch on the shape: when `LEDGER_REPO == REPO_ROOT`, log an informational line
naming the collapsed single-repo shape and saying the pre-tick contamination
guard is the control there — and skip the probe entirely, which is also the
cheapest way to stop the `.taskpump-rotest` probe file tripping the fs-guard
(issue #88; call that out in the commit so it is not fixed twice). Reserve the
`WARNING` wording for the separate-ledger shape, where a writable primary
genuinely is a regression. Both values are resolved long before the check.
Correct `runner.sh`'s mount-shape comment and `docs/RUNNERS.md` §4.3 in the same
pass: the self-check *reports the collapse*, it does not warn of a regression.

### #59 — "scheduled for deletion" schedules nothing

Three sites describe the legacy inline pre-flight fallback as awaiting removal:
`runners/claude-docker/README.md` (§The transitional fallback), and
`runners/claude-docker/entrypoint.sh` at roughly `:91` and `:384`. Nothing
schedules it — no issue, no milestone, no task file — and TaskPump's own root
still ships the `claude-settings-auto.json` marker that arms it, so a dogfood
run with no hook set takes the path presented as being on its way out. An
operator plans a migration against a deadline that does not exist; a maintainer
treats live code as dead code.

Substitute the truth at all three sites: the path is retained for the
transition, no removal date is set, nothing new should depend on it, and a
consumer that sets `TASKPUMP_PRE_FLIGHT` never reaches it. The README must also
state the fact the current text hides — that TaskPump's own checkout carries the
marker, so a dogfood run with no hook set does take this path.
`runners/claude-docker/preflight-example.sh` is in your footprint because
`entrypoint.sh:384` describes it as a copy of logic that is scheduled to go;
make its header say what is actually true. Do not remove the fallback itself:
that is separate work, and it changes behaviour.

### #105 — one runtime resolution, three verbs

`TASKPUMP_DOCKER` is how an operator points TaskPump at podman or nerdctl. The
runner honoured it in `list` (which delegates to `apl_docker`) and not in
`launch`/`stop`, so a podman host got a runner that enumerated the fleet
correctly and died with rc 127 on teardown — surfacing exactly when the docs
tell the operator to invoke the verbs by hand.

**This one appears to have landed in the 2026-08-19 sweep**:
`runners/claude-docker/runner.sh` resolves
`DOCKER="${TASKPUMP_DOCKER:-${DOCKER:-docker}}"` at a single site. Verify at
HEAD. If it holds, the residual is the two deliverables the sweep did not land:
the **regression anchor** in `tests/test-tp-runner-stop.sh`, and the docs row.
Record the verification in the completion note either way.
