# G4.1 — tp init scaffolds a new consumer

## Spec

`tp init` — the first command a new consumer runs:

- Writes a commented `taskpump.conf` at the enclosing worktree root, containing
  only the keys a starter actually decides (`TASKPUMP_TASKS_DIR`,
  `TASKPUMP_ID_PATTERN`, and a commented `TASKPUMP_BUILD_GATE`), with a pointer
  to `taskpump.conf.example` for the census. `--tasks-dir <d>` overrides the
  default `tasks`.
- Creates the tasks directory.
- Prints the next three commands (`tp task create …`, `tp task ready`,
  `tp pump --dry-run`) so the quickstart continues from the terminal.
- Refuses to run if a `taskpump.conf` already exists anywhere the discovery
  walk would find one, printing that path — init must never shadow an existing
  ledger's configuration. Re-running after a refusal changes nothing
  (idempotent failure).
- New `libexec/tp-init`, dispatched from `bin/tp`, listed in `tp help`.

## Scope

Scaffolding only. No git commits (the consumer decides when to commit the
conf), no task creation, no fsck (G4.2).

## Acceptance

- Hermetic suite: init in a scratch repo → `tp task create T1 …` →
  `tp task ready` works end to end with no further configuration.
- Second `init` exits non-zero naming the existing conf; the tree is
  unchanged (asserted by diff).
- `init` from a subdirectory writes the conf at the worktree root, not `$PWD`.
- CONFIG.md documents init as the recommended starting point.
