# G4.2 — tp task fsck validates and stamps existing ledgers

## Spec

The import path for a repository that already has a directory of markdown task
files. `tp task fsck` checks the whole ledger against LEDGER-CONTRACT:

- frontmatter parses as YAML between `---` delimiters;
- `id` matches the filename and `TASKPUMP_ID_PATTERN`;
- `status` is in the vocabulary; machine keys have contract-legal types;
- every blocker names an existing task; no self-blocking; no blocker cycles
  (the one check no single-file tool can do — a cycle silently removes its
  members from the frontier forever);
- report mode prints one line per violation (`<file>: <what>`) and exits 3 when
  any are found, 0 on a clean ledger — the same convention `scrub` uses for
  invisible files.

`--fix` stamps *missing* machine keys with the contract's defined defaults
(`status: open`, empty blockers, null claim fields, zero counters), never
touches the body, never rewrites a present-but-wrong value (report those;
guessing intent is how ledgers get corrupted), and commits through the standard
ledger-commit path so the repair is one auditable commit.

## Scope

`tp-task` verb + suite + a LEDGER-CONTRACT section documenting fsck as the
conformance tool (MINOR bump note in CHANGELOG). Body conventions
(Spec/Scope/Acceptance headings) are explicitly not checked — they are not
contract.

## Acceptance

- Fixture ledger with one of each violation class (bad YAML, id/filename
  mismatch, unknown status, dangling blocker, self-block, a 3-cycle): report
  mode names each on one line, exit 3.
- A "bare markdown" fixture (files with only `id`, `title`, a body) round-trips:
  `--fix` → fsck clean → `tp task ready` sees the tasks.
- `--fix` on a ledger with a wrong-typed *present* value changes nothing and
  still reports it.
- Clean ledger: exit 0, no output. `./tests/run-all.sh` green.
