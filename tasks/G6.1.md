# G6.1 — Hermetic suites and a fixture that passes its own fsck

## Spec

This task runs first and blocks the code lanes for one reason. Until it lands,
**an agent that runs `./tests/run-all.sh` inside its worktree can rewrite the
live supervisor's state in the primary checkout.** Three suites run real
`tp pump` ticks whose workspace resolution answers with the checkout the suite
was launched from, so they write or delete `.taskpump-fsguard.notified`,
`.taskpump-pool-cap`, `.taskpump-pump.state`, `.auto-trunk.lock` and
`.auto-trunk-quarantine` at that root. G6 is drained supervised, with a pump
running against this very repository, so that is not a hypothetical: it is one
agent re-arming or forging the notification and cap state of the supervisor
that dispatched it, mid-drain. Every other suite assertion this phase adds is
worth less than the guarantee that running it changes nothing outside its own
scratch directory.

Issues: **#111** (suite hermeticity and the blind gate) and **#76** (the
reference fixture fails its own fsck).

**Read the tree before you edit it.** The 2026-08-19 sweep landed a large part
of both issues after they were written, so the issue bodies describe a tree that
no longer exists in several places. Every file:line below is a starting point
for a search, not a coordinate — lines move. Verify each claim at HEAD first;
where a residual has already been closed, say so in the completion note rather
than re-closing it.

### #111 — the state-dir leak and the gate that cannot see it

What is wrong. `libexec/tp-pump` derives its whole run-state family from
`STATE_DIR="${TASKPUMP_STATE_DIR:-$REPO_ROOT}"` (around `tp-pump:232`), and
`run_pre_tick_hooks` both writes the hook mark file and, on the quiet branch,
`rm -f`s it (around `tp-pump:2339-2342`). A suite that runs a real tick without
pinning `TASKPUMP_STATE_DIR` inherits the checkout it is running from. The gate
that is supposed to catch this — `tests/run-all.sh` — snapshotted only
`git status --porcelain`, which is blind twice over: the run-state names are
gitignored, and porcelain compares entries rather than contents, so rewriting a
file that existed before and after is a diff of zero.

What already landed, verified at the time this task was written:

- `tests/run-all.sh` carries the per-suite manifest probe, the state windows,
  the live-pump attribution warning and the `.git/info/exclude` row. Its header
  argues, correctly, that a content manifest **supersedes** the
  `git status --porcelain --ignored` half of #111's proposed fix, because
  `--ignored` reports paths (missing the clobber) and reports every ignored path
  in a developer's tree (failing runs they did not cause). Do not add
  `--ignored` to satisfy the issue's checklist; record in the completion note
  that that bullet was deliberately superseded, and why.
- `tests/suite-prologue.sh` exports a per-suite `TASKPUMP_HOOK_MARK_FILE`
  (around `:84`), which is what actually stopped the `.taskpump-fsguard.notified`
  damage.
- `pump_tick` in `tests/test-tp-pump.sh`, `cap_tick`/`real_tick`/`rtick`/`ttick`
  in `tests/test-pump-task-grain.sh` and `probe_tick` in
  `tests/test-config-resolution.sh` each pin `TASKPUMP_STATE_DIR` by hand.

What must be true after:

1. `tests/suite-prologue.sh` **sets and asserts** a per-suite
   `TASKPUMP_STATE_DIR` under the suite's own scratch dir, so a suite written
   next year inherits hermeticity without opting in and a suite that unsets or
   overrides it fails loudly rather than silently leaking. Today the pins are
   per-helper and per-suite: they are three hand-copied backstops, not a rule.
2. `tests/run-all.sh` grows a self-check with both directions. Positive: plant
   a sentinel `.taskpump-fsguard.notified` with known contents at the repo root
   before the suites run, assert it is byte-identical after. Negative: a
   deliberately leaky stub suite that rewrites that sentinel **in place** must
   make the gate report FAILED — this is the case a path-set diff cannot see,
   and it is the assertion that proves the manifest probe has teeth rather than
   merely existing.
3. `CONTRIBUTING.md` states the hermeticity convention with all three legs —
   conf, env, **state dir** — where a contributor meets it. It is the only
   prose file this task owns; the third leg is currently written down nowhere a
   contributor reads.

### #76 — the reference ledger and the contract's executable form

`docs/LEDGER-CONTRACT.md` §11.1 calls `fsck` "the executable form of this
contract", and the fixture a new user copies once failed it with exit 3 out of
the box: `completed_by_commits` held an all-digit placeholder sha that YAML
types as a number, and `--fix` cannot repair a present-but-wrong value by
documented policy.

At the time of writing this looks closed at HEAD:
`tests/fixtures/generic-project/tasks/T1.md:12` carries a sha with hex letters
(the shape a real sha has, which YAML cannot mistype), and
`tests/test-tp-task-fsck.sh` (around `:675-711`) already sweeps every directory
under `tests/fixtures/` and asserts a clean `fsck`. **Verify, do not assume.**
Copy the fixture to a scratch dir, run `tp task fsck` and `tp task scrub`, and
confirm both are rc 0. If they are, the residual is the plan's added half only:
an assertion that `fsck --fix` **repairs a deliberately broken copy** — stamp a
missing machine key, prove `--fix` fills it, and prove a present-but-wrong value
is still left alone, because that policy at `libexec/tp-task:2591-2596` is what
the fixture repair depended on and nothing asserts it stays.
