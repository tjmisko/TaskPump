# G6.9 — Every flag means one thing, and the brief written is the brief rendered

## Spec

Six issues, two passes: one over the argument parsers of `tp pump` and
`tp task`, one over the template renderer and the two functions that write its
output to disk. They are one task because they are the same lines. #73, #132 and
#133 all rewrite the identical parser arms — a patch for any one of them touches
the other two — and #98, #100 and #134 all sit in the render path that consumes
what those arms set. Read all six with `gh issue view`. Every file:line below
comes from their evidence and every one of them moves the moment you edit;
locate by function name with `rg` and treat the numbers as a starting point.

**If your budget runs short, the split point is between the two halves.** #73 /
#132 / #133 (parsing) complete first and are independently shippable; #98 /
#100 / #134 (rendering) become the follow-on. Do not stop in the middle of
either half.

### The parser pass

**#73 — a value-less flag prints bash's crash text.** `tp pump --phases` with
nothing after it produces `libexec/tp-pump: line 341: $2: unbound variable` — no
tool-name prefix, no sentence, a line number inside a file the operator did not
write. `docs/CLI-PUMP.md:25` already documents the intended behaviour
(`--phases is required`, exit 1), so the code is failing to produce the message
it promises. Eight `tp-pump` arms and roughly 28 `tp-task` arms share the
unguarded `flag) VAR="$2"; shift 2;;` pattern; four arms in the same `tp-pump`
parser (`--jobs`, `--usage-ceiling`, `--tick`, `--resume-max`) are already
guarded and do the right thing. The unguarded `tp-pump` arms are around `:341`,
`:351`, `:356`, `:357`, `:359`, `:372`, `:374`; the `tp-task` sites are
enumerated in the issue (around `:538,540,650,652,800,873,875,1081,1083,1150,
1176,1206,1254,1548,1550,1552,1714,1716,1944,1946,1996,2028,2916-2926`).

After: a `need_val` helper beside `die()` in each tool —
`need_val() { [[ $# -ge 2 && -n "${2:-}" ]] || die "$1 needs a value"; }` —
called from every value-taking arm in both tools. Keep `exit 1`; no exit status
moves. Two details a naive patch gets wrong: the guard must fire **before**
`MODE` is mutated in the `--render-brief` / `--render-resume-note` arms, or a
later error reports the wrong mode and sends the reader to the wrong place; and
an empty string (`--phases ""`) must be rejected too, which is what the `-n`
conjunct buys.

**#133 — `--phases` and `--render-brief` write one variable and the later flag
wins.** Around `libexec/tp-pump:364-366` and `:395-398`, five arms all assign
`PHASES`. `docs/CLI-PUMP.md:125-127` states the rule with no order condition
("`tp pump --phases T2 --render-brief T1` renders T1's brief; the `--phases T2`
is discarded") and the tool only honours it when the render flag comes last.
Reverse them and the operator gets a correctly formatted, confidently labelled
brief for a unit they did not ask about, rc 0, no warning. The tell that this is
a code defect and not a docs gap: `templates/README.md:97-101` has already been
patched to tell authors "Do not add `--phases` to these commands", because the
tool cannot be trusted with both.

After: the four render arms write their own `RENDER_TARGET`; `--phases` keeps
`PHASES` for the snapshot range. When a render mode is selected, a non-empty
`RENDER_TARGET` is the unit to render whatever the argument order; an empty one
defaults to `$PHASES` so today's single-flag invocations are unchanged.
`render_brief_stream` / `render_resume_note_stream` read `RENDER_TARGET` while
the snapshot range stays `PHASES`. A hard refusal when the two disagree would
also close it but breaks an invocation the documentation currently defines — do
not do that here.

**#132 — `--render-brief` at phase grain accepts a task id and prints fiction.**
The `MODE=render` block (around `libexec/tp-pump:3074-3094`) refuses a *phase*
at `--grain task` with a six-line comment explaining exactly why, and has no
symmetric guard on the phase path. `tp pump --phases T2 --render-brief T2.1`
prints 130 lines of confident fiction at rc 0: the task id appears 25 times in
positions that mean "phase", the reader is told to run `tp task next --phase
T2.1` for a phase that does not exist, and is pointed at `tasks/T2.1.N.md`.
Anyone who overrides `TASKPUMP_TASK_BRIEF_TEMPLATE` and verifies it the
documented way silently verifies the *phase* template, gets rc 0, and ships an
unchecked task brief to every agent.

After: both guards live in one helper (`assert_render_target_matches_grain`)
called from both arms, so the pair cannot drift apart again — it drifted once
already, which is why one side carries a comment and the other carries nothing.
At phase grain, `[[ -n "${TSNAP_STATUS[$target]:-}" ]]` is the precise test for
"this is a task", and the refusal is the mirror image of the existing message,
naming both alternatives. `--render-resume-note` (around `:3095-3103`) reads the
same target and only half-guards: handed a task id it dies with `no stalled
orphan detected for phase T2.1`, which still calls the task a phase. Route it
through the same helper.

### The render pass

**#100 — the renderer corrupts on `&`, re-expands its own output, and truncates
in silence.** `apl_render_template` (`lib/pump-lib.sh` around `:42-74`) is the
one function that turns a template into the prompt an unattended agent runs on,
and it fails quietly three ways.

It substitutes by looping over `TPL_VARS` and reassigning the line each time, so
a value substituted for an early key is still in the string when later keys are
matched: the render depends on bash's hash order, and a value can expand
placeholders that were never in the template. On the observed ordering
`TASK_FILES` — the one untrusted value — is second, so a value placed there
expands `{{PROJECT_BRIEF}}`, `{{TASK_CLI}}`, `{{BASE}}` and `{{TASK_ID}}` out of
itself. The author already worked around the ordering by hand at
`libexec/tp-pump:1345`.

The same `${line//pat/rep}` construct gives `&` in the replacement its bash 5.2+
meaning of "the matched text", so a perfectly ordinary operator brief corrupts
with no adversary at all: `TASKPUMP_PROJECT_BRIEF='Read the R&D handbook…'`
renders as `Read the R{{PROJECT_BRIEF}}D handbook…`.

And the section machinery never checks its own balance. `skip_at` is raised when
a `{{#KEY}}` opens with no content and can only be lowered by a matching
`{{/KEY}}`; `depth` is never checked after the loop; `done < "$tpl"` returns 0.
A template with one missing `{{/VERIFY_CMDS}}` renders completely on a machine
where that key has content and **silently drops everything from the marker to
end of file** on a machine where it does not — which, for `VERIFY_CMDS`, is the
shipped default. In both shipped templates the dropped remainder is exactly
`## Boundaries` and `## Definition of done`. The agent launches with a brief
that says what to build and never says not to merge, not to push to the base
branch, not to leave the ledger claimed. rc 0, nothing logged, healthy launch
reported.

After: replace the key loop with a single-pass left-to-right scanner that never
re-reads what it emitted (the issue carries a working `apl__subst_line`). That
removes the `&` hazard entirely, because no pattern-substitution replacement is
used, and makes the render order-independent. Track the opening key on a stack
and verify each `{{/KEY}}` closes the key that is actually open; after the read
loop require `depth == 0` and return non-zero naming the template and the
unclosed key; make a `TPL_BLOCKS` path that does not exist a failure rather than
`cat … 2>/dev/null || true`. An unknown `{{PLACEHOLDER}}` fails under strict
mode, with `TASKPUMP_TEMPLATE_STRICT=0` as the documented opt-out for a consumer
with a knowingly partial template. Propagate every failure: `render_brief` and
`write_resume_note` must abort the launch on a non-zero render — a template that
will not render cleanly must never produce a launched agent. Delete the hand
pre-substitution at `libexec/tp-pump:1345` once ordering no longer matters.
`templates/README.md:60` documents `{{PROJECT_BRIEF}}` as a block placeholder
while the pump registers it in `TPL_VARS` as a scalar; correct the document.
`templates/README.md:96-98` moves from "asserted by the test suite" to "enforced
by the renderer", naming the failure mode.

**#98 — the brief is written with `>|` into a path the agent can replace with a
symlink.** `render_brief` (around `libexec/tp-pump:1354-1362`) and
`write_resume_note` (around `:1416-1421`) redirect with `>|` — a forced
overwrite that follows symlinks — into the agent's own worktree, at a fixed
documented filename, and the worktree is bind-mounted read-write into the
container. An agent replaces `.taskpump-phase-brief.md` with a symlink and
stalls; the pump reuses the worktree (`if [[ ! -d "$wt" ]]` — it exists, so
nothing is recreated), renders again, and truncates the symlink's target as the
operator on the host. Pointed at `~/.claude/CLAUDE.md` that is a persistent
host-wide instruction implant; pointed at a shell rc file it is code that runs
at next login. Nothing checks. Secondary: the file lands mode 644, so the
operator's project brief and verification commands are world-readable at a
predictable path.

After: in both writers, refuse a symlink destination by name, unlink before
creating, and write under `umask 077`:

```bash
[[ -L "$out" ]] && { warn "refusing to render through a symlink: $out"; return 1; }
rm -f "$out"                     # unlink-then-create: a TOCTOU swap lands on a fresh inode
( umask 077; render_brief_stream "$target" >| "$out" )
```

The `rm -f` is the load-bearing half — the `-L` test alone is a race. Propagate
the non-zero: a launch whose brief cannot be rendered safely aborts loudly and
never launches an agent with no brief. The in-container half of this issue
(`runners/claude-docker/entrypoint.sh`'s goal-note write and its `chmod 666`) is
**not yours** — see Scope.

**#134 — a false comment and fourteen stale citations.** The comment at
`libexec/tp-pump:1582-1585` tells the reader "the shipped templates call this
`{{BUILD_GATE}}`". No shipped template does — `rg -n BUILD_GATE templates/` hits
only `templates/README.md` — and `tests/test-entrypoint.sh:1020-1025` fails the
suite if one starts to. The identical alias in the brief map (around `:1528`)
carries no comment at all, so whichever a maintainer edits, the other gives no
warning. Rewrite the comment to what is true (it is a compatibility alias of
`{{VERIFY_CMDS}}`, kept so a hand-written template reaching for the older name
still renders, and `TASKPUMP_BUILD_GATE` is a different thing — the merge
queue's gate, not the per-task verification commands) and put the same note, or
a one-line pointer to it, beside the duplicate.

Separately, all 14 `libexec/tp-pump` citations in `templates/README.md` are
stale — following them lands on a bare `}`, a bare `fi`, a blank line,
`PUMP_LOG=…`, `CEILING="$2"`, `done`, `set -- $spec`, `case "$GRAIN" in`, a
`while IFS= read` loop and two comment blocks about unrelated mechanisms. The
issue carries the correct site for each in a table, including the note that the
two `{{BUILD_GATE}}` citations are swapped relative to their own tables. Correct
all 14 — **and correct them last**, after your own edits have moved the lines,
or you will re-stale them in the same commit. The prose in that document has
just been carefully repaired, which is what makes the wrong pointers expensive:
a reader who decides to check is punished for checking.

  are not yours.** G6.11 owns them and may be running in the same round as you.
- **Do not take the brief out of the agent's reach.** Rendering into an ops
  directory and bind-mounting it read-only is the durable fix for #98 and it
  changes the runner contract in two runners; it is a MINOR follow-on and it
  must not gate this patch.
- **Do not make `--phases`/`--render-brief` disagreement a hard error** (#133),
  and do not give `need_val` a new exit status (#73). Both would move a
