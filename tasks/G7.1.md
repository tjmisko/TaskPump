# G7.1 — A discovered taskpump.conf is data, and no conf-relative path leaves the workspace

## Spec

Right now, typing `tp task --help` inside a repository you cloned runs whatever that
repository's author put in `taskpump.conf`, as you, with your SSH keys, your
`GITHUB_TOKEN` and your `~/.claude` credentials. That is issue #77 and it is the reason
this task exists. The unattended-drain milestone this phase carries cannot be declared
before this lands: the project's own operating notes record running ledger commands from
agent worktrees as routine, so one steered agent becomes host code execution as the
operator. See the plan's `safe_to_self_drain_after` — G7.1 is one of the five named
preconditions.

This task blocks on **G6.13**, the v0.2.2 tag, and that blocker is load-bearing rather
than ceremonial. A task-grain range run plans every phase in range in one tick, so
without the barrier the scheduler would happily dispatch this MINOR change beside the
patch line and it would ship inside a PATCH tag.

Three issues, one file. Everything below is `lib/config.sh`; the three changes are in
three different functions but they are one pass over one file, which is why they are one
task. All line numbers below come from the 2026-08-19 sweep and have already moved once
(the functions named are at `lib/config.sh:144`, `:176`, `:251`, `:281` and `:340` at the
time of writing). Treat every citation as a starting point for a search on the function
name, not as a coordinate.

### #77 — a discovered conf is executed, not read

`tp__source_config` is the entire loader: it sets `allexport` and runs `. "$path"`. There
is no parser, no key filter, no allowlist. `TP_CONF_KEYS` is computed *after* the fact by
diffing `compgen -v`, so it records what the file happened to set rather than restricting
what it may set. Every tool calls `tp_load_config` at file scope — `libexec/tp-task`,
`libexec/tp-pump`, `libexec/tp-monitor`, `libexec/tp-cleanup`, `libexec/tp-init`,
`libexec/tp-dag-render`, `libexec/tp-stream-fmt`, the two watchdogs, all four gates and
both hooks — so the exposure is every verb including the pure help paths.

After this task:

- **Discovery and execution are separate.** `tp__source_config` keeps its current body
  for exactly one caller: a conf the operator named explicitly in `TASKPUMP_CONFIG`. Every
  *ambient* (walked-to) conf goes through a new parsing sibling that reads line by line
  and accepts only `[A-Za-z_][A-Za-z0-9_]*=value`. Any line containing `$(`, a backtick,
  `${`, `<(` or a trailing backslash continuation is refused, naming the file and the line
  number. No `.` and no `eval` on that path.
- **Keys are allowlisted, not diffed.** Only `TASKPUMP_*` and `ARACHNE_*` names may be
  assigned. `PATH`, `BASH_ENV`, `ENV`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `IFS`, `HOME`,
  `GIT_SSH_COMMAND` and every other `GIT_*` name are refused **by name**, with a warning
  that names the key. This is the half a parser alone does not fix: because the file is
  sourced under `set -a`, a bare `PATH=/attacker/shims` assignment needs no shell syntax
  at all and re-points `git`, `jq`, `yq`, `docker` and the runner. The sweep reproduced
  exactly that.
- **The refusal message names both migration paths.** Confs that rely on shell stop
  working when they are *discovered*: command substitution
  (`TASKPUMP_TASKS_DIR="$(pwd)/tasks"`), conditionals, loops, sourcing a sibling file, and
  command-valued keys whose values contain shell operators — `TASKPUMP_NOTIFY_CMD`,
  `TASKPUMP_BUILD_GATE`, `TASKPUMP_RECLAIM_CMD`, `TASKPUMP_IMAGE_BUILD` — which are still
  *stored* fine as plain strings but can no longer be *computed*. The two supported paths
  are: set `TASKPUMP_CONFIG` to the file's absolute path, or move the computation into the
  environment before invoking `tp`. Print both.

### #101 — the walk has no ceiling and the file has no owner

`tp__discover_config` walks up from `$PWD` and its only ceiling is the enclosing git
worktree root. `tp__git_toplevel` returns empty outside a repository, so the only
remaining stop is `/`: a `taskpump.conf` planted in `/tmp` or any other shared ancestor is
picked up and run. Nothing anywhere `stat`s the file.

After this task: when `tp__git_toplevel` is empty the walk stops at `$HOME`, overridable
with a new `TASKPUMP_CONFIG_CEILING`, never at `/`. And before a conf is read at all — by
either path — it is refused with a diagnostic naming the path and the permission bits when
its holder directory is group- or world-writable, or when the file is not owned by the
invoking uid (or root). The tool then continues with defaults rather than reading it. This
is the posture git took with `safe.directory` and direnv took with `direnv allow`, and it
costs a correctly-owned conf nothing.

The existing vendored-install and submodule/superproject ceiling extension inside
`tp__discover_config` exists for a real consumer shape and must behave exactly as it does
today. The existing config tests covering it stay green unchanged.

### #93 — an anchored path is never checked for containment

`tp__anchor_conf_paths` makes a conf-relative value anchor to the conf's own directory,
then concatenates and exports it with no `realpath`, no `..` rejection and no assertion
that the result is still inside the workspace. Its only cleanup is stripping a trailing
`/.`. So `TASKPUMP_TASKS_DIR=../../../../somewhere/else` resolves exactly there and
`tp task create` writes and commits task files into it. The sweep observed
`resolve --all` printing `tasks_dir …/sk10/../sk10-escaped-tasks` and
`task_out …/sk10/../.next-task`, both labelled `via conf-value`, with `tp task list` then
reading the outside directory.

The symlink form needs no conf at all: the workspace probe is a bare `-d` test, which
follows symlinks, so a repo shipping `tasks -> /elsewhere` is accepted as the workspace's
ledger and every read and write follows the link out. Reproduced under `TASKPUMP_NO_CONF=1`.

This is the variant that survives a conf hardened to plain `key=value` with a key
allowlist, which is why it is in this task rather than folded into #77.

After this task: after `val="$anchor/$val"`, normalise with `realpath -m` and assert the
result is inside the anchor; when it is not, refuse in the same named-key, name-both-fixes
style the function already uses for the unanchorable case — print the key, the offending
value, the workspace root, and the two ways to fix it (an absolute path, or a value inside
the workspace). And the ledger probe compares `realpath` of the probe directory against
`realpath` of the candidate workspace, so a symlinked `tasks/` is refused rather than
followed. An absolute path outside the workspace, explicitly configured, still works — the
rule is about *conf-relative* escapes, not about forbidding external ledgers.

## Scope

The declared `files:` list is `lib/config.sh`, `docs/CONFIG.md`,
`tests/test-config-resolution.sh` and `tests/test-conf-hermeticity.sh`. Nothing enforces
that list but you. Two other agents are working `libexec/tp-task` and `libexec/tp-pump` in
this same wave; a stray edit to either collides with them.

`docs/CONFIG.md` is this phase's config-doc owner and you own it. That means sibling
tasks in G7 will hand you config-key documentation debt in their completion notes — the
new `TASKPUMP_SUBMODULE_INIT` row from G7.3 and any projection-path key from G7.4 among
them. Land what has arrived by the time you write; record anything you could not.

You may **not** touch `CHANGELOG.md` or `taskpump.conf.example`, even though this is a
behaviour change an operator must be told about and #77's proposed fix asks for both.
Those two files belong to **G7.9**, the phase tail. Write the migration story into
`docs/CONFIG.md` (the "File syntax" section, the discovery section, and the
conf-relative-paths section all change), and record the CHANGELOG and
`taskpump.conf.example` debt explicitly in your completion note so G7.9 lands it.

Do not attempt to make `TASKPUMP_GATES` conf-relative anchoring work — that is #122's
relative-first-word question and it belongs to **G7.3**.
