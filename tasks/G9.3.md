# G9.3 — A relocated ledger, worktrees dir and state dir are found where the conf put them

## Spec

Two issues — #118 and #107 — that are one property: a consumer repository that
already has opinions about its own layout relocates the ledger, the worktrees
directory or the state directory, and every tool must agree about where they
went, from any working directory.

File:line citations below come from the issue text. **Line numbers move**; treat
each as a starting point and grep for the identifier named beside it.

### #118 — `tp task` ignores `TASKPUMP_TASKS_SUBDIR`, so the pump reports DONE over live work

`TASKPUMP_TASKS_SUBDIR` is documented as the fallback spelling for
`TASKPUMP_LEDGER_PROBE`. `tp pump`, `tp monitor` and `tp dag-render` honour it;
`tp task` does not. The pump's frontier comes from the ledger CLI, so an operator
who sets `TASKPUMP_TASKS_SUBDIR=planning` gets two halves of one system reading
two different directories: `tp task` reads `tasks/`, finds nothing, and the pump
prints `DONE T1 (no open tasks)` over a phase full of open work. Nothing warns. A
drain that should have launched agents reports itself finished — the exact
false-drain failure this whole range exists to remove.

The divergence point is exact. `libexec/tp-task:35` calls `tp_load_config`;
`libexec/tp-task:65` then unconditionally does `: "${TASKPUMP_LEDGER_PROBE:=tasks}"`;
`libexec/tp-task:101` calls `tp_resolve_workspace`, whose first line
(`lib/config.sh:218-220`) is
`local probe="${TASKPUMP_LEDGER_PROBE:-${TASKPUMP_TASKS_SUBDIR:-tasks}}"` — by
then the probe is always set, so the `TASKS_SUBDIR` arm is dead code on this
path. `libexec/tp-task:146` then derives `TASKPUMP_TASKS_DIR` from the
already-defaulted probe.

What must be true after:

- The premature default at `libexec/tp-task:65` is gone. There is exactly **one**
  expression in that file that decides the ledger's location: resolve into a
  local before `tp_resolve_workspace` is called —
  `_tp_probe="${TASKPUMP_LEDGER_PROBE:-${TASKPUMP_TASKS_SUBDIR:-tasks}}"` — and
  use that same local at both the resolution site and the `TASKPUMP_TASKS_DIR`
  derivation.
- Everything downstream reads the **resolved** value, including `tp task --help`'s
  key list (`libexec/tp-task:3206`, `:3302`, `:3312`), which today renders the
  literal `tasks`.
- `TASKPUMP_LEDGER_PROBE` still wins when both keys are set.
- `TASKPUMP_TASKS_SUBDIR=planning tp pump --dry-run --phases T1` and
  `TASKPUMP_LEDGER_PROBE=planning tp pump --dry-run --phases T1` produce
  identical plans.

The issue notes `tests/test-example-confs.sh:481` asserts the extracted default
and may need updating. **That suite is not in your declared `files:` list.**
Prefer a change that leaves the assertion true. If it cannot be left true, edit
that one assertion and say so explicitly and loudly in your completion note — it
is outside your footprint and the next agent must know it moved.

### #107 — a relocated worktrees or state dir follows `$PWD`, and the heal targets the wrong directory

Two failures, one capability.

**Not anchored.** `TP_ANCHORED_PATH_KEYS` (`lib/config.sh:251-255`) contains no
`WORKTREES_DIR`, no `PUMP_WORKTREES_DIR`, no `STATE_DIR`, so a relative value in a
checked-in `taskpump.conf` resolves against `$PWD`. Running `tp pump` from the
repo root and from a subdirectory gives one repository **two disjoint fleets of
worktrees and two disjoint state files** — the same banner text naming two
different files on disk. This is the shape of issue #1, which the anchoring list
was built to close, left unfixed for these three keys. They meet the same test the
eleven current entries meet: a checked-in conf value describing a location inside
the workspace. `tp__anchor_conf_paths` already implements the
explicit-`TASKPUMP_CONFIG`-with-no-workspace refusal these keys need, and
environment values stay unrewritten per the documented edge.

**The heal is keyed to the wrong variable.** The launch guard refuses a
gitignored worktree, and the self-heal writes git negations for
`TASKPUMP_WORKTREES_IGNORE_LINE` — a separate key defaulting to `.worktrees/`
that is never derived from the worktrees dir. A consumer who moves worktrees into
`build/`, `dist/`, `out/` or `tmp/` — the obvious choices, and the ones nearly
every Node, Java and CMake `.gitignore` already ignores — gets every unit skipped
on every tick forever while the heal appends `!.worktrees/` negations for a
directory that project does not have. `tp pump --once` still exits 0.

Your half of this is `hooks/gitignore-repair:42-43`, which takes its `probe_base`
from `TASKPUMP_WORKTREES_IGNORE_LINE`. It must derive the repo-relative worktrees
base from the **resolved worktrees directory**, treating
`TASKPUMP_WORKTREES_IGNORE_LINE` as an override rather than the source of truth.

**The `lib/pump-lib.sh` half is not yours.** `apl_repair_worktree_gitignore` and
`apl_ensure_worktrees_visible` (cited at `:159` and `:186`) have the identical
defect — `apl_ensure_worktrees_visible` is *handed* the real path as `$probe` and
then ignores it when composing the negation — and so does the refusal diagnostic
in `libexec/tp-pump:1522-1531`. Both files belong to co-scheduled siblings this
wave (G9.1 owns `lib/pump-lib.sh` and `libexec/tp-pump`). Do not edit them.
Record the pump-lib half as a named follow-on in your completion note, with the
two function names, so it is visible to G9.6's reconciliation rather than lost:
until it lands, the capability is only half repaired and your acceptance must say
which half you proved.
