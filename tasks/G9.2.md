# G9.2 — The workspace, not the installation, is what the disk tools act on

## Spec

Five issues — #113, #106, #115, #121, #114 — and one property: **the tools act on
the workspace the operator is standing in, and on the directories that workspace
actually configures.** They are one task because #113 and #114 cannot be
separated from each other or from the rest: both span `libexec/tp-pump`,
`libexec/tp-cleanup`, `libexec/tp-disk-watchdog` and `lib/pump-lib.sh`, and a
split gives two agents the same four files.

Every file:line below comes from the issue text. **Line numbers move**, and
several of these sites have already shifted or been partly repaired at HEAD.
Verify each site before editing; where a code half is already landed, what
remains is the assertion and the document that would have caught it.

**This task is the phase's largest. If you are running short of budget, the plan
names the split point: land #113, #115, #121 and #106 — the rooting and the busy
set — and complete. #114 (the reclaim precondition) is then a follow-on that
must be recorded by id in your completion note, not silently dropped.**

### #113 and #106 — the roots

Two unattended safety nets decide which repository they are protecting by walking
up from their own script directory. In a consumer repo that is the **TaskPump
installation**, not the operator's workspace.

- The disk watchdog writes its emergency pool cap into a file the running pump
  never reads. The operator sees `pool cap → 0` in the watchdog log while the
  pump keeps launching at cap 4 until the disk fills.
- `tp cleanup --stuck` looks for agent logs under the *installation's*
  `.worktrees`, finds nothing, and prints `no stuck agents found` about a fleet it
  never looked at. `tp agent-watchdog` has no `REPO_ROOT` of its own — it delegates
  at `libexec/tp-agent-watchdog:75` — so it cannot correct it. A wedged agent is
  never committed, never stopped, and holds its ledger claim until a human
  notices. Both tools report success.

Sites: `libexec/tp-disk-watchdog:49-52` and `libexec/tp-cleanup:62-67`, each
deriving `_default_repo_root` from `"$(dirname "$0")/.."`; `libexec/tp-cleanup:208-213`
(`worktree_for_container`) and `:236-242` (`do_stuck`) build on it. `libexec/tp-pump`
does it correctly through `tp_resolve_workspace` (`lib/config.sh:219-235`).

At HEAD `tp-disk-watchdog` already resolves through `tp_resolve_workspace`;
`libexec/tp-cleanup` still does not. What must be true after:

- Both tools source `lib/config.sh`, call `tp_resolve_workspace`, and default
  `REPO_ROOT` to `TP_WS_ROOT`. `TASKPUMP_DISK_REPO_ROOT` and
  `TASKPUMP_CLEANUP_REPO_ROOT` remain the override seams —
  `tests/test-tp-cleanup.sh` pins the latter in every existing case and must keep
  working unchanged, which is also why those cases could never have caught this.
- Parents export their resolved paths to their children so the three processes
  cannot disagree: the `nohup "$DISK_WATCHDOG_BIN" --auto-exit` spawn in
  `libexec/tp-pump` (cited at `:2949-2953`) exports `TASKPUMP_POOL_CAP_FILE="$CAP_FILE"`
  and `TASKPUMP_STATE_DIR="$STATE_DIR"`; `libexec/tp-agent-watchdog:75` and the
  watchdog's own `tp-cleanup` invocation pass `TASKPUMP_CLEANUP_REPO_ROOT="$REPO_ROOT"`.
- `apl_read_cap` accepts `0`. The reader used to require `>= 1`, so the one number
  the watchdog ever writes fell through to the caller's `JOBS` and the pump kept
  launching at full cap through the pressure the watchdog had already logged. At
  HEAD this is landed together with a staleness window; confirm it and keep the
  assertion — garbage still falls back to `JOBS`, `0` does not.
- The empty stuck result becomes honest: `do_stuck` and `do_status` distinguish
  "no containers" from "containers whose worktree I could not find under
  `<WORKTREES_DIR>`", and name the directory searched, so a wrong root is visible
  from the output instead of requiring the reader to know the derivation.

### #115 and #121 — the busy set has no producer, and half of it was inert

`tp cleanup --targets` deletes build output. `EXTRA_BUSY_DIRS` is the list of
workspaces it must leave alone — the escape hatch for a workspace that is
mid-compile, where deleting the build directory corrupts a running build. The
tool's own help promises that "the disk guard passes compiler-busy workspaces
here" and that a listed primary root is skipped **even under `--include-primary`**.

- **#121:** the guards at `libexec/tp-cleanup:329-331` and `:345-347` read the
  **unprefixed** name only, so an operator following the naming convention every
  other key uses gets `rm -rf` on exactly the workspace they were protecting, and
  a summary reporting `skipped 0 live`. At HEAD the union of both spellings is
  landed (`BUSY_EXTRA_CANONICAL` / `BUSY_EXTRA_LEGACY`); confirm it, keep the log
  line naming which spelling matched, and keep the union rather than a fallback —
  a `${TASKPUMP_...:-${EXTRA_...}}` fallback would silently drop one of the two,
  which is the same class of bug being fixed.
- **#115:** **nothing in the tree ever sets the variable.** `rg -n EXTRA_BUSY_DIRS`
  over non-`.md` files matches the conf example, one test that sets it by hand,
  and the readers. `reclaim_targets` in `libexec/tp-disk-watchdog:139-150` — the
  only in-tree caller of `--targets --include-primary`, and the exact caller the
  help text names — builds the argv and exports nothing. So when the disk crosses
  the PANIC threshold the sweep runs against the primary checkout with the
  documented protection never fed, and a human's in-progress build is deleted out
  from under them. Compute the busy set in `reclaim_targets` and pass it on the
  invocation. At minimum it contains the pump's own workspace when a build is in
  flight, plus anything named by the operator's key. If the busy set genuinely
  cannot be computed honestly, the alternative is to *retract* the claim — delete
  the parenthetical in the help that names a caller which does not exist and say
  the key is operator-supplied only. Wiring is preferred; shipping neither is not
  an option.
- `docs/design/f90-addenda.md:38-39` asserts that `tp cleanup` "still honours"
  `TASKPUMP_EXTRA_BUSY_DIRS`. Whatever the outcome, that sentence must end up
  true; it is the one surviving doc that contradicts the code.
- `docs/PUMP-MECHANISMS.md:314-333` names two bounds on the reclaim sweep and the
  tool advertises three. That file belongs to G9.1 in this phase — record the
  mismatch in your completion note rather than editing it.

### #114 — reclaim is gated on a directory named `target/`

The bounded-disk-footprint property a multi-day drain depends on is the reclaim
pass. Both paths first check for a directory literally named `target/` — Rust's
build directory — and skip anything else. On a Node, Python, Go or Java project a
consumer who does exactly the right thing and sets
`TASKPUMP_RECLAIM_CMD='npm run clean'` gets a pass that executes nothing and
**prints nothing**, because the "unconfigured" diagnostic is guarded on the key
being *empty*. The disk fills and the log does not say why.

At HEAD the `tp-cleanup` half is landed: `reclaim_target` executes
`TASKPUMP_RECLAIM_CMD` with the workspace as cwd, behind an optional
`TASKPUMP_RECLAIM_DIR` probe. The **pump half is not**. In
`reclaim_done_targets` (cited at `libexec/tp-pump:2275-2297`, at HEAD around
`:2477-2499`):

- Drop `[[ -d "$wt/target" ]] || continue`. Keep the `unit_live` skip — that one
  is a real safety bound.
- Replace the `du -sh "$wt/target"` pre-measure with a worktree-level size delta
  (measure before and after) so the log line stays useful, and change the log
  wording from `reclaimed $p target/` to name the **workspace**, not a Rust
  directory.
- If a precondition is wanted at the pump site, spell it with the key
  `tp-cleanup` already reads — `TASKPUMP_RECLAIM_DIR` — rather than inventing a
  second key or a literal. Reconcile the two sites on one key and one default,
  and state that default in `docs/CLI-TOOLS.md`. The plan's "optional
  `TASKPUMP_RECLAIM_PROBE` with an always-run default" and the shipped
  `TASKPUMP_RECLAIM_DIR` are the same idea; do not ship both names.
- While in `tp-cleanup`, replace the two-level `*/*` glob at `:322` and `:389`
  with `find "$WORKTREES_DIR" -mindepth 1 -maxdepth 2 -type d`, which closes the
  DEFERRED note the file carries at `:318-321` — a branch prefix without a slash
  (`TASKPUMP_BRANCH_PREFIX=''`) makes every worktree invisible to the sweep
  today. Delete or correct the `CARGO_TARGET_DIR` claim in the comment at `:288`:
  nothing in the tree reads that variable.

Note the suite bakes the defect in: `tests/test-tp-pump.sh:447-450`'s
`plant_target()` creates `target/` before every reclaim assertion, so no existing
test can observe the skip. **Add a case; do not edit the helper.**
