# G4.6 — No tp pump exit path leaves the state file claiming status running

## Spec

Issue #22: after the G3 drain, `.taskpump-pump.state` still read
`status: running, live_agents: 1, open_tasks: 6` with no supervisor, no
container, and a reverted T1 inflating the count. Two exit paths never reach
`write_state drained` (`libexec/tp-pump:1633`):

1. `--once` exits right after `do_tick` (`libexec/tp-pump:1610-1614`), whose
   last write is `write_state running` — every single-tick run abandons a
   `running` state file.
2. A killed loop (Ctrl-C, crash, `systemctl stop`) dies wherever it was;
   there is no trap.

A reader deciding "is a pump live?" from this file gets the wrong answer —
the failure mode that has burned a rescue session before.

The fix, in two halves:

- **Writer honesty.** `--once` writes a terminal state before exiting; an
  EXIT/INT/TERM trap in loop mode stamps `stopped` (with the reason) so no
  exit path can leave `running` behind.
- **Reader skepticism.** `write_state` records the pump's `pid` (and host);
  liveness readers (`tp monitor`, anything else consuming the file) verify
  the pid with `kill -0` and present `status: running` with a dead pid as
  STALE, never as a live pump. The state file becomes a hint, not an oracle.

## Scope

`libexec/tp-pump` (write_state, the --once tail, the loop trap),
`libexec/tp-monitor` (stale detection + rendering), and their suites. The
`open_tasks` count is a per-tick snapshot and stays one — staleness labeling
is what makes the snapshot age visible.

## Acceptance

- After `tp pump --once`, after a SIGTERM'd loop, and after a completed
  drain, the state file never reads `running`.
- `tp monitor --glance` against a `running` state file whose pid is dead
  labels the pump STALE and says since when (last_tick).
- The suites cover all three exit paths and the stale-render, with a
  positive control (a live-pid `running` file renders as running).
