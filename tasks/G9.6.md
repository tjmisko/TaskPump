# G9.6 — A repository that is not this one, and is not Rust-shaped, drains

## Spec

This task carries no issue number. It is the phase's demonstration: G9.1 through
G9.5 each removed a default that made TaskPump work here and fail elsewhere, and
this task turns the phase's promise — *runs in any repository* — from an argument
into a green suite. The operator is not asked to adopt the tool on the strength
of five completed tasks.

### The repository it runs against

Not this one, and not a copy of `tests/fixtures/generic-project` — that fixture
was built to this project's shape and shares its assumptions. `tests/fixtures/foreign-consumer`
is a **seed tree**, checked in, that the suite copies into a scratch directory and
`git init`s inside the job. Nothing in it may be TaskPump-shaped:

- **Not Rust.** No `Cargo.toml`, no `target/`. Give it a shape a reader
  recognises as somebody else's project — a `package.json` and a `Makefile`, or
  a `pyproject.toml` — and a reclaim command that belongs to it.
- **A relocated ledger.** The tasks subdirectory is not `tasks/`; use
  `planning/`, configured with `TASKPUMP_TASKS_SUBDIR` (the alias spelling, which
  is the one G9.3 made live under `tp task`) rather than
  `TASKPUMP_LEDGER_PROBE`, so the drain exercises the repaired path.
- **A non-`.md` extension.** `TASKPUMP_TASK_EXT=.task`, the key G9.4 made live in
  the writer.
- **No `ops/` anywhere**, and none may appear during the run.
- **A `.gitignore` that already ignores the directory the worktrees go into** —
  `build/` with worktrees relocated under `build/wt` — so the visibility heal
  from G9.3 is exercised rather than assumed.
- **A remote that is not `origin`.** Create a bare repository in the scratch
  directory and add it as `upstream`, so G9.5's `TASKPUMP_REMOTE` / configured-
  upstream resolution is under test. If G9.5's completion note recorded the
  non-`origin` push-retry assertion as owed to this suite, it lands here.

The run environment must be as hostile to the old defaults as the fixture:
`HOME=$(mktemp -d)` with **no `~/.claude`**, **no `TASKPUMP_IMAGE`**,
`TASKPUMP_RUNNER=runners/local/runner.sh`, and `TASKPUMP_LOCAL_AGENT_CMD` set to
a stub agent — a small script that writes a marker commit and marks its task
done, so the drain completes deterministically without a model. No container
runtime may be required to run this suite; CI must be able to execute it on a
box with no docker and no podman.

### What counts as a pass

`tests/test-generic-consumer.sh` drives the whole adoption path in order and
asserts each step, so a failure names the step that broke rather than the tail:

1. `tp init` scaffolds the consumer, and the tick that follows emits **no
   `FS-GUARD` output** (G9.1).
2. `tp task create` writes task files that carry the configured extension into
   the configured directory — assert the path on disk, not the tool's own report.
3. `tp task ready` returns a non-empty frontier, run **from the repository root
   and from a subdirectory**, resolving to the same ledger both times (G9.3).
4. `tp pump --dry-run` plans the same units `tp task` sees. The two halves
   agreeing is the assertion that would have caught the false-DONE family: a
   plan that says `DONE (no open tasks)` while `tp task ready` lists work is the
   failure this whole range exists to remove.
5. A **task-grain drain across two phases** runs to completion: every task ends
   `done`, the second phase's tasks launch only after their blockers close, and
   the run exits 0 because it finished, not because it found nothing.
6. Throughout: no entry is written to the quarantine file; no directory named
   `ops/` exists anywhere under the consumer afterwards; the reclaim command
   configured in the fixture actually ran (assert its marker), on a project with
   no `target/`; and `tp dag-render` and `tp monitor --glance` both see the tasks
   under the non-`.md` extension.

Assert the negatives explicitly. "No `ops/` was created" and "the quarantine file
is empty" are the two that silently regress, and a suite that only checks the
happy path will not notice either.

`.github/workflows/ci.yml` runs this suite as its own step, on a runner with no
container runtime, so the phase's promise is checked on every push rather than
once.

### The key census

The second half of this task is the reference catching up with five tasks' worth
of changed defaults. Do it **mechanically, not by reading**:

- Extract every `TASKPUMP_*` key named in `docs/CONFIG.md` and in
  `taskpump.conf.example`.
- Extract every `TASKPUMP_*` key actually read under `libexec/`, `lib/`,
  `gates/`, `runners/` and `hooks/`.
- Reconcile the three lists. **Both directions are findings**: a key the
  documents describe that no tool reads, and a key a tool reads that no document
  names. For every key that survives, check the *default* the document states
  against the default the code now uses — the defaults are what this phase
  changed, and a stale default in the reference is exactly the kind of
  false-but-plausible sentence that sends the next consumer down a dead end.
- The keys created or moved in this phase are listed in the completion notes of
  G9.1 through G9.5. **Read all five before starting the census** — those notes
  are the only channel those tasks had, and each one lists doc-debt sites by path
  and line for you to land.

Then land the phase's own documentation: every doc-debt site recorded by G9.1
through G9.5 that falls inside your declared files, README's adoption and
runner-choice sections (§6 currently teaches `TASKPUMP_IMAGE=unused-…` as the way
to run without containers and must stop), and a `CHANGELOG.md` entry for v0.3.0
covering the phase — the keys that went from inert to live, the defaults that
moved, and the behaviour changes each implies for an existing consumer.

Where a recorded doc-debt site is **not** in your declared files, do not edit it:
carry it forward in your own completion note so it is still visible to the next
phase. G9.1 recorded at least `docs/RUNNERS.md` §4's mount table and
`runners/claude-docker/README.md`; G9.3 recorded the `lib/pump-lib.sh` half of
#107; G9.4 recorded the shared `ps` extraction and
`runners/claude-docker/runner.sh:120`. Those are follow-ons, not yours.

## Scope

The declared `files:` list is the whole footprint. Nothing enforces it but you.

This task **fixes no tool**. If the drill fails, that is the point of the drill —
but the repair belongs to whichever task owns the file, not here. A tool defect
this suite uncovers becomes a new task with its own id, named in your completion
note; a red suite you fixed by editing `libexec/` is a phase whose demonstration
proves nothing. The only exception is the fixture and the suite themselves.

`CHANGELOG.md` belongs to this task alone in this phase, by the project's own
G2.3 precedent. `docs/CONFIG.md`, `taskpump.conf.example` and `README.md`
likewise: no sibling touched them, which is why the census can be a single
reconciliation rather than a merge.

Do not add this suite to `tests/run-all.sh` if that file is not in your declared
list — wire it into CI and record the run-all registration as a one-line
follow-on.
