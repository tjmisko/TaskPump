# G6.5 — The vendored-install marker cannot be forged

## Spec

Issue **#94**. The question "is this directory a vendored TaskPump checkout?" is
answered by testing for two filenames, and nothing checks that the files are
TaskPump's, that they are non-empty, or that either is executable:

```sh
tp__is_taskpump_install() {
  [[ -f "$1/lib/config.sh" && -f "$1/libexec/tp-task" ]]
}
```

around `lib/config.sh:103-105` — a starting point for a search, not a
coordinate; lines move.

Any repository a victim adds as a git submodule can `touch` those two paths and
thereby claim to be a TaskPump install. Two things then change for anyone
standing inside that submodule. Workspace resolution jumps to the
**superproject**, so `tp task claim`, `complete` and `release` typed inside the
dependency mutate the parent project's ledger. And the config discovery walk
extends its ceiling into the superproject, so a `taskpump.conf` at that
directory is passed over. Reproduced with a control: a submodule containing only
two empty files resolves `cwd_root` and `tasks_dir` to the superproject, while
an ordinary submodule with its own `tasks/` and no marker files resolves to
itself.

Rated honestly: this is not an attacker-initiated action and there is no
execution. It redirects a command the *victim* typed toward the victim's own
superproject, and in the conf case it makes the walk trust the parent more
rather than less. It is a robustness bug on a trust boundary — and this
project's own operating notes already record the same class of confusion as a
painful lesson ("`tp task` mutations run from a worktree write the worktree's
private ledger; always `cd` to the primary first"), which is why it is worth
closing rather than documenting.

What must be true after. `tp__is_taskpump_install` identifies what its own
comment says it identifies — "the structural marker, independent of which copy
of the tools is actually running" — with evidence a stub cannot fake. Require
all of: `libexec/tp-task` exists **and is executable**; `lib/config.sh` is
non-empty and carries TaskPump's own sentinel (a grep for the `tp_load_config`
function definition is the cheapest honest one); and preferably a positive
marker only a real install ships — a `VERSION` file alongside both, whose
content matches the semver shape.

The change belongs in the one helper, because three call sites depend on the
answer: `tp__conf_is_vendored_install` (around `:124-129`), the ceiling
extension in the discovery walk (around `:162`), and `tp_workspace_cwd_root`
(around `:197-200`). Do not fix it three times.

The issue #6 shapes must keep working. A genuinely vendored TaskPump submodule
is still recognised, including its conf-skipping behaviour, and a nested plain
clone still keeps its own conf. If your marker is strict enough to break either,
it is too strict — the regression tests for #6 are the boundary.

This task is blocked on **G6.1** because it edits the resolution path the suites
themselves exercise, and until the suites pin their state dir, running
`tests/test-config-resolution.sh` from a worktree writes the primary's run
state. Do not start before G6.1 is done.

## Scope

Declared footprint: `lib/config.sh` and `tests/test-config-resolution.sh`. This
task is deliberately small and deliberately alone: it is the **only**
`lib/config.sh` change on the PATCH line, and keeping it alone is what keeps
that file out of every other G6 wave. Nothing enforces the footprint but you.

Explicitly not yours, and each is a real temptation while you are in this file:

- The `. "$path"` conf source under `set -a` in `tp_load_config` (around
  `:179-181`) — the conf-as-shell RCE, issue **#77**. It is the single most
  serious open defect in the repository and it is **G7.1**'s, on the MINOR line,
  because closing it changes what a conf file may contain. Do not touch it. Do
  not "harden it a little" on the way past. If you notice something new about
  it, write it in the completion note.
- `libexec/tp-task`, `libexec/tp-pump`, `lib/pump-lib.sh` — **G6.2** and
  **G6.7** this wave.
- `docs/CONFIG.md` — **G6.13** owns every shared document at the phase tail.
  The sentence describing what now counts as a vendored install is doc debt:
  write it in your completion note in the form G6.13 can paste.

      `tasks_dir` as the **submodule** root, not the superproject.

      genuinely vendored TaskPump submodule**, built from a real install copy,
