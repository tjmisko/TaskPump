# G8.4 — A task file from outside the trusted set is held, not scheduled

## Spec

A task file is an instruction stream. The pump reads `tasks/*.md` and renders their
prose into the kickoff brief an autonomous agent receives as its instructions, and the
ledger is writable by anyone who can open a pull request. Nothing anywhere asks **who
wrote this task**. The eligibility predicate has no author dimension at all: a task is
schedulable when its `status` is `open` and its blockers are `done`. That is fine when
every task file came from someone you trust, and it is exactly what makes "point
TaskPump at a repository you do not control" unsupportable — a stranger's pull request
that adds a task file is a stranger's pull request that writes the instructions for an
agent holding real credentials, a real checkout and days of unattended runtime.

This is **#138**, and `docs/THREAT-MODEL.md` §5 names it as one of two controls that
would move Tier 3 off "do not". G8.1's fence limits what injected text can *say*; this
task answers whether the text should have been scheduled at all.

After this: with a trusted set configured, a task file whose last-writing commit falls
outside it is held out of the eligible frontier, **reported** with its author and the
reason wherever the frontier is reported, and released only by an explicit human act
that the ledger records. Unconfigured, nothing changes at all.

### The design decision, and how to stop debating it

The substance of #138 is what "trusted" is keyed on. There are three candidates and
the issue costs one of them: **ship "present at range start"**, document the other two
in `docs/THREAT-MODEL.md`, and do not spend the budget on the argument.

- **Present at range start** (ship this) — cheapest, needs no key distribution, and
  covers the PR-stream case exactly, which is the case Tier 3 is about.
- **Author allowlist** — the weak form; defeated by a forged author field unless
  commits are signed. Document it as the shape a consumer wants when agents file
  follow-up tasks during a drain, since an agent commits under a known identity.
- **Signature requirement** — the strong form; needs a key distribution story this
  project does not have. Document it as the v1.0.0 direction.

Mechanically, "present at range start" is one configuration key naming a git revision
— call it `TASKPUMP_TRUSTED_SINCE` — resolved in the repository that holds the ledger,
which is not always the code repo. A task file is **in the trusted set** when the
commit that last wrote it is an ancestor of that revision:

```sh
git -C "$ledger_repo" log -1 --format='%H%x09%an%x09%ae' -- "$task_file"
git -C "$ledger_repo" merge-base --is-ancestor "$sha" "$TASKPUMP_TRUSTED_SINCE"
```

Unset key: the gate is off and every code path must be byte-identical to today's.
Derive the anchor from an operator-set revision, **not** from pump state — a range that
restarts must not silently re-anchor and launder the files added since.

Three edge cases you must decide and document rather than leave to the implementation:

- A task file that is **untracked or uncommitted** has no provenance at all. With the
  gate on it is **held**, not trusted. Say so in `docs/LEDGER-CONTRACT.md`; a
  hand-edited working tree is the case an operator will hit first.
- A file whose last-writing commit is **not reachable** from the anchor at all (a
  different history, a shallow clone) is held, with the reason distinguishing
  "outside the trusted set" from "cannot be evaluated".
- The **ledger's own commits** — the ones `tp task` makes as it claims, completes and
  heartbeats — must not hold the task they touch. Key on the commit that last changed
  the task's *body and identity*, or exclude the tool's own committer identity, and
  say which you chose and why. Getting this wrong turns the gate on and empties the
  frontier one tick later.

### Where the predicate lives, and the trap in it

The eligible frontier is computed **twice, deliberately**. `cmd_ready` in
`libexec/tp-task` (cited `:629-748`) carries a comment saying its predicate is
"parallel to (not factored out of) `cmd_next`" (cited `:534-627`) so the hot path stays
byte-for-byte. A provenance gate added to one and not the other is precisely the
false-drain failure this whole project exists to prevent: `ready` would report a held
task while `next` handed it to an agent, or the reverse. Update both, and make the
suite assert they agree on the same fixture.

`--count-eligible` must not count held tasks. `--count` (the drain test) must still
see them, because a ledger with held work is not drained.

### Held is reported, never invisible

An invisible task is the family this project already has issues for. A held task must
appear:

- in `tp task ready` (both the default and `--json` shapes) marked `held: provenance`
  with the author name and email from the last-writing commit, and the anchor it failed
  against;
- in `tp pump --list` (`MODE=list`, the one planning pass) in the same terms, so an
  operator reading the plan sees why the frontier is short.

Author strings come from a commit message in a repository you do not control, so they
are repository data: run them through **G8.1**'s `apl_display_data` before they reach a
terminal or a rendered plan. Do not print an un-sanitised `%an`.

### The release is a human act, recorded

Add a release verb to `libexec/tp-task` — `tp task trust <id> --reason "..."` — which
stamps the release into the task's frontmatter (the releasing identity, the timestamp,
the reason, and the sha that was released) and commits it, so the release is in the
ledger and reviewable in the diff. Document the new keys in
`docs/LEDGER-CONTRACT.md` §3 alongside the existing frontmatter contract.

The release must not be reachable from a pump-launched agent — an agent that can
release its own planted task has bought nothing. Reuse the caller-identity check
**G7.2** landed across the ledger verbs rather than inventing a second mechanism; if
what you find there does not extend to this, the minimum is refusing when the pump's
agent-session marker environment is present, and that limitation goes in
`docs/THREAT-MODEL.md` in as many words rather than into a comment.

Releasing a task whose file changes again after the release must re-hold it: the
release records a sha, not a permanent exemption.

## Scope

The eight paths in `files:` above and nothing else. Nothing enforces the list but you.

Do not touch:

- **`lib/pump-lib.sh`.** You call `apl_display_data` from **G8.1**; you do not change
  it. If it does not do what you need, say so in the completion notes rather than
  editing a file this task does not own.
- **The rendering fence, the template keys and the runner capability verb** — G8.1 and
  **G8.3**, both landed before you. Your held-task reporting rides on them.
- **`docs/CONFIG.md` and `taskpump.conf.example`.** `TASKPUMP_TRUSTED_SINCE` needs a
  row in both and they belong to **G8.5**. Document the key fully in `docs/CLI-PUMP.md`
  and `docs/CLI-TASK.md`, and record the CONFIG.md and conf-example debt in your
  completion notes for G8.5 to land.
- **`docs/LEDGER-CONTRACT.md` §10.** No reserved exit code moves. A held task is not an
  error: `ready` and `--list` still exit 0 with held work in the ledger, and a refused
  `trust` exits 1, the generic failure §10.1 already documents.
- **The policy root** (#78/#139) — **G7.7**'s, already landed. This gate is the other
  half of Tier 3's precondition, not a re-litigation of that one.

`docs/THREAT-MODEL.md` is shared with **G8.5**, which runs strictly after you; write
your §5 Tier-3 changes now and leave the coverage claim about the injection corpus to
it.
