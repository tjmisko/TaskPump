# G6.12 — The hostile-ledger drill

## Spec

This task carries no issue of its own. It is the phase's promise turned into a
green suite, and it gates the v0.2.2 tag: G6.13 blocks on it, so nothing ships
until this drill passes.

The claim G6 makes is that the ledger is **data**. Three siblings each made one
part of that true in their own file, and each proved it with assertions written
against the site they were repairing:

- **G6.2** (#89) — ledger text and agent-log text reach the terminal as text.
  `tp task list`, `tp monitor`'s SESSIONS panel, `tp stream-fmt` (which printed
  through `echo -e`, so a literal backslash-e in a file became a real ESC) and
  the pump's own WAITING and stall lines all wrote control bytes straight
  through. The dashboard is the control loop; a forged dashboard is how a red
  run reads green for a day.
- **G6.3** (#95, #80, #99) — no ledger string is reparsed as shell.
  `tp cleanup --stuck` built a command string out of a task id and `eval`ed it,
  and did the same with a worktree directory name; the claude-docker entrypoint
  interpolated the lead task's id into its session script five times, running as
  the `dev` user at bootstrap with `GITHUB_TOKEN` already in scope and before
  `claude -p`'s permission classifier exists. Both watchdogs run `tp cleanup`
  unattended, which is the whole point of the tool.
- **G6.9** (#100, #98, #132, #133) — the brief written is the brief rendered. An
  `&` in a value corrupted the render, an unclosed section marker truncated the
  brief from the marker to end of file (dropping exactly `## Boundaries` and
  `## Definition of done`) at rc 0, and the brief was written with `>|` through
  whatever the destination path happened to be, including a symlink an agent
  planted into its own worktree.

Each of those is pinned where it was fixed. What nothing pins is the
**composition**: one ledger carrying all of them at once, driven through the
tools an operator actually runs, asserting that every payload lands inert and
**named**. Named matters as much as inert. A ledger entry that a tool silently
skips is invisible to the frontier, and an invisible task is the false-drain
failure this project exists to prevent — so "it did nothing" is not a pass; "it
said which file, which field and why" is.

### The fixture

`tests/fixtures/hostile-ledger/` is a ledger tree built to attack its own
supervisor. It carries, at minimum, the payloads the 2026-08-19 sweep actually
recorded — read the issues for the exact bytes rather than inventing your own:

1. **A task id containing a single quote and a semicolon** (#95, #99) — the id
   that closed `tp-cleanup`'s quoting and the entrypoint's single-quoted
   literal. The shell fragment must be an inert canary (a `touch` of a path
   inside the fixture's temp tree), never anything destructive.
2. **A worktree directory name containing an apostrophe** (#80) — the
   directory-listing half of the same defect.
3. **CSI and OSC sequences in a task `goal:` and in an agent log tail** (#89) —
   including the literal backslash-e form, which is what `echo -e` amplified
   into a real ESC. Cover at least: erase-screen plus cursor-home followed by a
   forged green summary, cursor-up plus erase-line overwriting a real failure
   row, and an OSC window-title rewrite.
4. **A brief template with an unclosed `{{#VERIFY_CMDS}}`** (#100) — rendered
   both with the key populated and with it empty, since the truncation only
   appears in the empty case and the empty case is the shipped default.
5. **A value containing `&`** (#100) — in `TASKPUMP_PROJECT_BRIEF` and in a
   `files:` entry, so both the operator-supplied and the ledger-supplied paths
   are covered.
6. **A symlinked brief destination** (#98) — `.taskpump-phase-brief.md`
   pre-created in a fixture worktree as a symlink to a canary file, with the
   resume-note twin on the resume path.

Add anything else the sweep recorded that these six do not reach; the list is a
floor, not a ceiling.

### The drill

`tests/test-hostile-ledger.sh` drives that one fixture through the four
surfaces an operator uses, in this order, and asserts on each:

- **`tp task`** — `list`, `ready` (table and `--json`), `next`, `fsck`. Every
  hostile id is either rendered inert or refused **by name**; `fsck` names the
  file and the field rather than accusing the whole ledger or passing it. A
  hostile row must never simply vanish from `ready`.
- **`tp pump --dry-run`** (plus `--list` and `--render-brief`) — the plan prints,
  the wait reasons print, no payload reaches the terminal as a control byte, the
  unclosed marker makes the render fail naming the key instead of truncating,
  and the symlinked destination is refused with the canary byte-identical
  afterwards.
- **`tp cleanup --dry-run`** — with the hostile ids and the quoted worktree name
  in front of it, and with `tp agent-watchdog`'s unattended invocation shape
  represented, since that is the caller that runs with nobody watching.
- **`tp monitor`** — one non-interactive paint over the fixture, asserting the
  SESSIONS panel and the log tail carry no raw ESC.

The assertions that make it a drill rather than a smoke test:

- **No host command runs.** Every payload's shell fragment writes a named canary
  path; assert every canary is absent at the end. Put a recording stub ahead of
  the real tools on `PATH` for anything the drill should never invoke and assert
  it recorded zero calls.
- **No false success.** Every refusal is non-zero where a refusal is the
  contract, and every tolerated payload is reported — assert on the message, not
  only on the status.
- **No forged terminal.** Assert through `cat -v` (or an equivalent byte check)
  that no `ESC` reaches stdout for any of the four surfaces, and that the
  visible text still contains the payload's readable part, so the fix is
  sanitising rather than swallowing.
- **Every assertion is mutation-checked.** For at least the id-injection, the
  unclosed-marker and the symlink cases, revert the sibling's fix locally and
  confirm the drill goes red. A drill that cannot fail is not a drill.

Safety, because this suite runs on the operator's machine and in CI: everything
happens inside a throwaway tree removed on exit, with a stub `docker` and a stub
runner; no container starts and no real agent launches; no payload fragment does
anything but `touch` inside that tree; and every invocation is pointed
explicitly at the fixture through the environment, never discovered ambiently.
`tests/suite-prologue.sh` is sourced like every other suite.

Two things to check before you write a line. The fixture is deliberately
**invalid** — that is its purpose — so make sure no existing suite enumerates
fixture ledgers and asserts they pass `tp task fsck` (G6.1 has just landed #76,
which made `tests/fixtures/generic-project` fsck-clean). If one does, keep the
hostile ledger outside that enumeration rather than editing a suite you do not
own. And run-all's hermeticity gate compares a status snapshot and a run-state
manifest before and after every suite; the drill must leave the checkout exactly
as it found it, or the gate will correctly blame you.

## Scope

You may edit exactly the three paths in this task's `files:` list. Nothing
enforces that list but you; G6.10 is dispatched beside you in this round on the
strength of it.

- **Fix nothing.** This task adds a suite and a fixture. If the drill finds a
  hole that G6.2, G6.3 or G6.9 did not close, that is a finding — record it in
  your completion note, naming the surface and the payload, and if it is
  material to the tag say so plainly so G6.13 can decide. Do **not** reach into
  `libexec/`, `lib/`, `gates/`, `hooks/` or `runners/` to patch it; you would be
  editing files those tasks own and the tag would ship a change nobody reviewed
  against its issue.
- **`tests/run-all.sh` is yours this round**, but you need it only if the
  hermeticity gate or the litter manifest needs an allowance for the new
  fixture. Suite discovery is automatic — `find "$SCRIPT_DIR" -maxdepth 1 -name
  'test-*.sh'` around `tests/run-all.sh:201` — so do not add a hand-maintained
  suite list.
- **No other `tests/test-*.sh` is yours.** Every sibling's own assertions stay
  where they are; this drill is the composition, not a second copy.
- **Keep the fixture self-contained.** `tests/fixtures/hostile-ledger` is
  declared as a single directory path, and until G7.8 lands the scheduler's
  disjointness check is an exact string comparison — do not create anything
  under a path another task declares, and do not touch
  `tests/fixtures/generic-project`.
- **The ledger goes one level down, and this is not a style preference.**
  `tests/test-tp-task-fsck.sh` sweeps *discovered* fixtures —
  `find "$TP_ROOT/tests/fixtures" -mindepth 1 -maxdepth 1 -type d`, gated only
  by `[[ -d "$fixture/tasks" ]]` — and asserts every one of them fscks clean at
  rc 0 with no output. Your fixture is deliberately invalid, so the natural
  layout, `tests/fixtures/hostile-ledger/tasks/`, would be swept and would turn
  that suite red. You cannot repair it: `tests/test-tp-task-fsck.sh` is G6.1's
  file, G6.1 completed long before you, and its own acceptance requires the
  sweep to keep working. So nest the ledger — `tests/fixtures/hostile-ledger/
  repo/tasks/` — leaving no `tasks/` directly under the fixture root, and say in
  your completion note that the nesting is load-bearing so nobody flattens it
  later. This is a semantic collision no disjointness check can see: the two
  tasks' `files:` lists really are disjoint.
- `CHANGELOG.md` and `VERSION` belong to G6.13 alone.
