# G3.6 — Refuse loudly when no ledger probe answers instead of falling back to the install root

## Spec

Discovered live by G2.1's verification agent (2026-08-12): when neither an
explicit tasks dir, a discovered conf, nor the cwd's git toplevel answers the
ledger probe, workspace resolution falls back to the *installation root*
(`_tp_repo_root="$_tp_script_root"`, `libexec/tp-task:71` area). A `tp task
create` run in a fresh repo with no `tasks/` directory therefore wrote a task
into the TaskPump checkout's own dogfood ledger — silently, with a git commit.
The agent caught it only because the enclosing repo's ledger was under watch.

The fallback exists for the vendored-per-worktree layout, where each worktree
carries both its own copy of the CLI and its own ledger — in that layout the
install root IS the workspace, and the probe above it answers anyway. The
defect is the *silent* part: a bare consumer repo that simply forgot `mkdir
tasks` gets no error, no hint, and a mutation landing in a ledger it has never
heard of.

Ledger-*mutating* commands (`create`, `claim`, `complete`, `block`, ...) must
refuse loudly when resolution reaches the install-root fallback AND the
resolved ledger is not within the caller's own git worktree: name what was
probed (`$TASKPUMP_LEDGER_PROBE` from the cwd toplevel, the discovered-conf
anchor if any), name where resolution ended up, and say `mkdir tasks` (or
`TASKPUMP_TASKS_DIR=...`) fixes it. Read-only commands (`resolve`, `list`,
`ready`) may keep working — `resolve` is the diagnostic the error points at.
The vendored layout must keep working unchanged: when the install root lies
inside the caller's worktree (or IS the caller's worktree), the fallback is
correct and stays silent.

## Scope

`libexec/tp-task` resolution/guard only, plus tests. Do not change the probe
order or the discovered-conf anchoring (G1.6); this is a guard on the last
fallback, not a resolution redesign.

## Acceptance

- In a scratch repo with no `tasks/` and no conf: `tp task create T1 ...`
  exits non-zero with an error naming the probed locations and both fixes;
  nothing is written anywhere; `tp task resolve --tasks-dir` still prints
  where resolution would land.
- In the vendored layout (CLI inside the workspace, ledger at the probe above
  it) every existing suite case still passes — the fallback stays silent where
  it is correct.
- A regression test covers the exact G2.1 incident shape: fresh git repo, no
  `tasks/`, TaskPump installed OUTSIDE it, mutation refused, install ledger
  untouched.
