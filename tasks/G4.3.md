# G4.3 — Provide tp inside the agent container

## Spec

Complete what G1.6 started: the in-container default is `tp` on PATH, so the
reference runner must put it there.

- `runner.sh launch` bind-mounts the TaskPump installation directory (resolved
  from the runner's own realpath, the same way `bin/tp` finds its libexec)
  read-only at a fixed in-container path (`/opt/taskpump`).
- The entrypoint prepends `/opt/taskpump/bin` to the agent's PATH before
  resolving the task CLI, so resolution order becomes: explicit
  `TASKPUMP_WORKSPACE_TASK_CLI` → `tp` on PATH (now guaranteed) → the loud
  error from G1.6 (now unreachable with the shipped runner, kept for custom
  runners).
- The mount is read-only and the tools resolve siblings install-relative
  (`TP_LIBEXEC_DIR` et al.), so nothing writes into it and worktree/ledger
  resolution still follows the *caller's* cwd, per the wrong-ledger lesson.
- RUNNERS.md documents the mount as part of the reference runner's contract,
  and that a consumer image needs bash/git/yq/jq for tp to function — the
  preflight hook is where a consumer asserts that.

## Scope

The reference runner and entrypoint only. Baking tp into images, or packaging
it, is out of scope. Arachne keeps `scripts/arachne-task` via its conf pin
until F90 retires it — the pin must keep winning over the mounted tp
(resolution order above guarantees it).

## Acceptance

- `test-entrypoint.sh` asserts the resolution order: pinned workspace CLI wins;
  unset → mounted tp found; mount absent + unset → the G1.6 error.
- The docker-argv golden assertions in `test-tp-pump.sh` include the new `-v
  …:/opt/taskpump:ro` mount.
- A container launched by the reference runner can run `tp task claim` against
  the mounted ledger with no vendored CLI in the workspace (integration-style
  test with the stub docker, asserting the composed argv and env).
