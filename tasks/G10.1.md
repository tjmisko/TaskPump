# G10.1 — A pause is not health, and a failing launch is not progress

## Spec

`tp pump` is a supervisor. Everything it reports today — the stall counter, the
WAITING line, the state file — is derived from the *plan it computed*, not from
*what the tick actually did*. So a pump that starts nothing, forever, looks
exactly like a pump that is working, and `systemctl --user status` stays green
through all of it. Four issues are four doors into that same room, and all four
are one pass over `libexec/tp-pump`'s tick body. Do them in one commit series on
one branch; splitting them across tasks would mean three agents editing the same
two hundred lines.

**Which side moves: the code.** The frozen exit-code table at
`docs/LEDGER-CONTRACT.md` §10 (around `:692-707`) is **not edited by this task**.
No code changes meaning: 3 still means deadlock, 0 still means "this invocation
finished". What changes is *when* 3 is produced and *what the state file can tell
a reader*. Both are consumer-visible, which is why this is v0.3.0 and not a
patch, and both need a migration note (below). §10.1 — the conformance note, not
the table — is where the closures and the notes are recorded.

Every `file:line` below comes from the issue and was true at the revision the
issue was written against. **Line numbers move.** Treat each as a starting point:
find the function or the arm by name, confirm the code still says what the issue
says it says, and if it does not, say so in your completion note rather than
editing by coordinate.

### #112 — the deadlock detector reads the plan, so a failing launch never exits 3

The counter (`libexec/tp-pump:2491-2496`) increments only when the plan is empty:

```
  if (( have == 0 )) && [[ -z "${PLAN_LAUNCH[*]:-}" && -z "${PLAN_RESUME[*]:-}" ]]; then
    STALL_TICKS=$((STALL_TICKS + 1))
  else
    STALL_TICKS=0
  fi
```

and the loop test it feeds is at `:3025`, `(( STALL_TICKS >= STALL_EXIT_TICKS ))`.
`launch_unit` (`:1477`) returns 1 on three refusal arms — the gitignored-worktree
refusal (~`:1529-1531`), the trunk-conflict refusal (~`:1543-1545`), the runner
failure (~`:1605-1606`) — and **removes nothing from `PLAN_LAUNCH`**. So a
repository whose worktrees the operator's global `core.excludesFile` happens to
ignore, or a host whose runner will not start, produces an unbounded series of
ticks that each planned work and each started nothing, with `live_agents=0`,
`open_tasks>0` and `status=running`. Measured: a stub runner exiting 1 gave eight
consecutive `runner failed to launch T1 (rc=1)` warnings and the run only ended
on SIGTERM.

After this task the predicate is outcome-shaped: a tick that ends with nothing
live and nothing started made no progress, whatever the cause; a tick that
launched something, or that has live agents, is progress.

Three things ride with it.

- **`stall_exit`'s reason string** (~`:2530-2560`, notified at `:2548`) must name
  the last launch failure when the stall was driven by refusals. As written it
  would page a human saying "nothing launchable" about a plan that was full,
  which is worse than silence. Have `launch_unit`'s three refusal arms record a
  last-failure reason for it to quote.
- **`--jobs 0`.** `:344-346` accepts it (`^[0-9]+$`) while `:362` immediately
  below rejects 0 for `--resume-max` (`^[1-9][0-9]*$`). Tighten the flag to match.
  A cap **file** containing 0 must still be honoured as a pause: that is the disk
  watchdog's throttle, and after G9.2 `apl_read_cap` honours a written 0, so a
  cap-0 tick that fell through to the new outcome-shaped counter would page a
  human for a throttle that is working exactly as designed. A tick at cap 0 logs
  `PAUSED feeding`, writes `status=paused` with a reason, and **returns before the
  counter**.
- **Docs.** Delete the known-bug section at `docs/CLI-PUMP.md:86-105`, and make
  the tick-order and deadlock prose at `docs/CLI-PUMP.md:695-715` and in
  `docs/PUMP-MECHANISMS.md` state the outcome-shaped predicate.

Note what §10.1's third paragraph already says today: *"The pump asks the
question one step later: nothing live and **nothing started**, for N consecutive
ticks."* That sentence is currently false — it describes the fix, not the code.
This task is what makes it true. Do not delete it; verify it word by word against
what you land.

### #131 — one WAITING line for a dead end and for an ordinary wait

`compute_plan_task`'s `open` arm (`:2404-2413`) tests a blocker's status only for
`== "done"`. Everything else becomes an undifferentiated `pending` entry, so

```
  WAITING  T2.1      (blockers pending: T1)     <- T1 is blocked: permanent
  WAITING  T2.2      (blockers pending: T2.1)   <- T2.1 is open: transient
```

render identically and count into the same `N waiting` summary, which reads as
healthy backpressure. A range whose only remaining work sits behind a dead end
ticks forever, because from the plan's point of view everything is merely
waiting.

Split the message while accumulating `pending`, using the blocker's status from
`TSNAP_STATUS`:

- `blockers pending: <ids>` — blockers that are `open` or `in_progress`.
- `blocked on a dead end: <id> (<status>) — needs a human` — when any blocker is
  `blocked`, `needs-review` or `stuck`.

Route the dead-end case into the **deadlock predicate you are already rewriting
for #112**, so a range whose remaining units are all behind dead ends exits 3
rather than ticking. A *mixed* range — one dead end, one transient wait — keeps
ticking and must not exit 3.

Second half, in `libexec/tp-task`'s `cmd_block` (`:1146-1170`): after the write,
scan the ledger for tasks listing this id among their blockers and print the
blast radius at the moment the operator causes it —
`blocked T1 — 2 dependent task(s) now ineligible: T2.1, T2.2`. Today `cmd_block`
prints `blocked T1` and nothing else.

`tests/test-tp-task.sh` is **not** in your `files:` list. Drive the `cmd_block`
assertion from `tests/test-pump-wait-reason.sh`, which already resolves the real
tool as `REAL_TASK="$TP_ROOT/libexec/tp-task"` and is yours; if you conclude it
genuinely belongs in the tp-task suite instead, leave it out and record it as
test debt for G10.3, which owns that file.

### #75 — phase grain has no escape hatch for a blocker branch that never existed

At `--grain task`, `unit_deps_integrated` (`:1178-1197`) treats a blocker whose
branch does not exist in this repository as integrated, and says why in its own
comment: *"holding a unit forever behind a branch that will never exist is a
stall, not a safeguard."* At `--grain phase`, `phase_deps_integrated`
(`:1148-1159`) lacks the `rev-parse --verify refs/heads/$dbranch || continue`
guard and deadlocks the range instead — and phase is the default grain. Same
ledger, same repository, same flags but for `--grain`: one plans `LAUNCH`, the
other sits `WAITING` until `STALL_EXIT_TICKS` and exits 3. Any repository that
adopted TaskPump after some of its work was done, or that deletes branches after
merge, cannot drain at phase grain under `--integration-trunk` at all.

Give both functions **one shared existence-check helper** rather than duplicating
the line, and let the `:1178-1181` rationale comment become the shared rationale.
Keep the strict reading reachable:
`TASKPUMP_PUMP_INTEGRATION_REQUIRE_BRANCH=1` restores today's behaviour, and
under it the wait reason must **name the missing branch** — that is the whole
value of asking for strictness. `docs/CLI-PUMP.md:367-405` (§5.1) currently
presents the deadlock as the expected outcome; rewrite it to the new default plus
the opt-out key.

The new key also belongs in `docs/CONFIG.md` and `taskpump.conf.example`. Neither
is in your `files:` list. Record both as doc debt in your completion note,
addressed to G11.3 (`docs/CONFIG.md`) and G11.4 (`taskpump.conf.example`).

### #72 — eight invocations exit 0, one is a drain, and the state file cannot tell

§10 says exit 0 means, for the pump, **drained**. Eight `tp pump` invocations
reach exit 0: `--help`, `--list`, `--dry-run`, `--render-brief`,
`--render-resume-note`, `--detach`, `--once`, and the loop drain. Six of them
write no state file at all, so the contract's own fallback ("read the state
file") hands the reader the *previous* run's terminal status with nothing in it
to say which invocation wrote it. `(rc=0, status=stalled)` is producible from a
healthy `--list`. The sharpest case is `--detach`: it returns 0 immediately, in
the foreground process, before the run it started has ticked once.

Additive fix; the frozen table is not touched.

1. `write_state`'s jq object (`:2589-2608`) gains **`mode`** (`loop|once|detach`)
   and **`invocation_id`** (`"$$:$PUMP_STARTED_AT"`). Every existing key keeps its
   name, type and meaning.
2. `detach_and_exit` (`:2775-2792`) stamps before exiting 0:
   `status: "handed-off"`, `mode: "detach"`, reason naming the unit or pid and
   saying this invocation did not tick.
3. `--list`, `--dry-run`, `--render-brief`, `--render-resume-note` and `--help`
   keep writing **nothing** — `docs/CLI-PUMP.md:157` promises `--dry-run` is
   side-effect-free and the suite asserts it — and each prints one line to
   stderr: `# no state written (plan mode)`. Silence that is explicit is not the
   same as a write that failed.
4. `libexec/tp-monitor` (`:688-772`) is the only in-tree state-file reader. It
   must render `handed-off` distinctly from `running` (a detached parent is not a
   live pump) and must tolerate a state file with **no `mode` key**, which is what
   every v0.2.x file looks like.
5. `systemd/taskpump-pump.service:60-68`'s comment records why that unit is
   correct — it happens to run loop mode — and states the new rule.

The consumer rule becomes checkable: **drained iff `status == "drained" && mode
== "loop"`**. Put that in §10.1's state-file remedy, replacing the advice written
for v0.2.x readers (keep the historical statement labelled as such).

### The two migration notes

Both go in §10.1 in this commit, and both are quoted verbatim into CHANGELOG by
G10.4 — record them in your completion note so that task can lift them.

- **`--grain phase` treats a blocker whose branch does not exist as integrated.**
  A range that previously sat WAITING and eventually exited 3 now drains. If you
  kept every pump branch and relied on the strictness, set
  `TASKPUMP_PUMP_INTEGRATION_REQUIRE_BRANCH=1`. No exit codes change.
- **The state file gains `mode` and `invocation_id`, and `--detach` stamps
  `status: "handed-off"`.** Readers switching on `status` must add a `handed-off`
  arm; it is not `running` and it is not an outcome. A file with no `mode` key was
  written by v0.2.x and is unattributable. Plan modes still write nothing and now
  say so on stderr, which a strict stderr parser will see.

A third consumer-visible change needs a sentence even though no code moves:
**exit 3 is now produced in situations that exited 0 before** — an every-launch-
fails run and a range behind a dead end. A supervisor with `Restart=on-failure`
will start restarting runs it used to leave alone. Say so.
