# G11.3 — A first-time operator gets from clone to a supervised drain from the docs alone

## Spec

This range changed defaults, flags, exit codes, refusal messages and the state
file. Every one of those changes has a documentation site, and the documentation
was written by people who already knew the answer. The reader this task is for
has not: they have a clone, a repository they want drained, and the README. If one
command on that path has a stale flag, an undefined placeholder or an outcome that
no longer happens, they stop there, and nothing in the tree would have told us.

G6.11 created `docs/RUNBOOK.md` and `tests/test-docs-claims.sh`, which today
asserts the README index is complete and that following the adoption `.gitignore`
leaves a first run's tree clean. This task turns the suite into what its name
promises: every fenced command on the adoption path and in the runbook is
**executed** in a scratch repository and its stated outcome asserted.

### Executable, verbatim, cold

- Extract every fenced command from README's adoption path and from
  `docs/RUNBOOK.md` and run each in a scratch repo built inside the suite. Run
  them in the order the document gives, because the ordering is part of the claim.
- Each command needs an **assertable stated outcome** — an exit status, a line the
  output must contain, a file that must exist or must not. Pick a convention for
  carrying that in the document (an annotation comment the suite parses, or an
  expected-output block), document the convention in the suite's header and in the
  runbook, and make an **un-annotated command on the adoption path a failure**. If
  a new command can be added without a test, the suite decays back into the review
  it replaced.
- Cold-read means the path is self-contained: no `<your-repo>` placeholder without
  a definition, no "as above", no command that only works if you already ran
  something the document does not show. Where a placeholder is unavoidable, the
  suite substitutes a defined value and the document says what it is.

### The runbook answers by symptom, for the failure modes this range created

`docs/RUNBOOK.md` is organised by what the operator sees, not by what the code
does. Every diagnostic this range introduced needs an entry, because an operator
meeting a brand-new refusal message with no runbook entry assumes a bug:

- a gate chain that cannot run refusing instead of printing `GATE: feed-ok` (#122);
- a `taskpump.conf` refused by name — a command in the conf, a `PATH` assignment,
  a conf found above the worktree (#77);
- a ledger mutation refused because the claimant is not the caller (#83, #84, #90),
  and a task held because its provenance is not trusted (G8.4);
- two co-scheduled tasks refused for an overlapping footprint under the new
  containment grammar (#91);
- `WAITING … blocked on a dead end` versus an ordinary pending wait (#131);
- a stall exit whose reason names the last launch failure, and a tick at cap 0
  reporting `paused` rather than ticking toward a deadlock (#112);
- a state file reading `status: handed-off`, and the rule that a drain is
  `status == "drained" && mode == "loop"` (#72);
- exit **2** from `tp task` / `tp pump` where an integrator's script expected 1
  (#71);
- the disk watchdog writing a cap the pump now honours, including 0 (G9.2);
- a phase waiting on a blocker branch that never existed, and
  `TASKPUMP_PUMP_INTEGRATION_REQUIRE_BRANCH=1` for anyone who wants the old
  strictness back (#75).

Each entry: the symptom as it appears on screen, what it means, what to do.

### The key census, asserted rather than reviewed

G9.6 reconciled `docs/CONFIG.md` against what the tools read. Make it mechanical
and bidirectional: extract every `TASKPUMP_*` / `TP_*` / `ARACHNE_*` name read by
`bin/`, `lib/`, `libexec/`, `gates/`, `hooks/` and `runners/`, and assert (a) every
key read is documented, and (b) every key documented is read somewhere. The second
direction is the one that catches a key renamed in code and left standing in the
docs, which is how an operator ends up setting something that does nothing.
`TASKPUMP_PUMP_INTEGRATION_REQUIRE_BRANCH` arrives here as debt forwarded from
G10.1 via G10.4 and must be in the census.

If the census disagrees with `taskpump.conf.example`, that file is **not** yours —
it is G11.4's. Record the delta in your completion note addressed to G11.4, and
make the suite's assertion cover only `docs/CONFIG.md` so it does not go red on a
file the task cannot fix.

## Scope

Four paths: `README.md`, `docs/RUNBOOK.md`, `docs/CONFIG.md`,
`tests/test-docs-claims.sh`. Nothing enforces that but you.

**Two siblings are running beside you.** G11.1 owns
`.github/workflows/ci.yml` and the generic-consumer suite; G11.2 owns
`tests/run-all.sh`, `SECURITY.md` and `docs/THREAT-MODEL.md`. `run-all.sh`
discovers your suite by glob, so you need no edit there; if the suite needs a
hermeticity-manifest entry, that is G11.2's file and goes in your completion note.

When a documented command turns out to be false, the default repair is the
document — that is this task's job. When the *tool* is wrong, file it and record
it; `bin/`, `lib/`, `libexec/` and `gates/` are not yours, and G10.3 has just
finished a sweep across all of them.

Do not touch `VERSION`, `CHANGELOG.md` or `taskpump.conf.example`. G11.4 cuts the
release and owns all three.

- [ ] A command on the adoption path with no assertable outcome annotation fails
      the suite; the convention is documented in the suite header and the runbook.
- [ ] The adoption path is cold-readable: every placeholder is defined in the
      document, and the suite substitutes the same definitions it states.
- [ ] `docs/RUNBOOK.md` has a by-symptom entry for every diagnostic listed above,
      each giving the on-screen symptom, its meaning and the action.
- [ ] The `docs/CONFIG.md` key census is asserted in both directions — every key
      read by the tools is documented, every key documented is read — including
      `TASKPUMP_PUMP_INTEGRATION_REQUIRE_BRANCH`.

      assertion.
