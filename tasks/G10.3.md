# G10.3 — Every tool exits 2 for a bad argument and nothing else moves

## Spec

`docs/LEDGER-CONTRACT.md` §10 reserves exit **2** for "Bad CLI arguments, any
tool", the row is frozen, and a consumer is invited to key on it. It does not hold
for the two tools the contract is about. Every usage error in `tp task` and
`tp pump` — unknown verb, unknown flag, a required value omitted, a value out of
range — routes through a `die()` that exits **1**, the same code `tp task next`
uses for "empty frontier" and the same code every operational failure uses. A
supervisor cannot tell a typo from a failure from nothing-to-do, and a CI job that
keys 2 to "bad arguments" never fires for the two commands it wraps.

It is worse than a uniform miss. Exit 2 *is* produced — by `bin/tp`'s dispatcher,
`tp init`, `tp cleanup`, both watchdogs and both shipped runners — so 2 means
"bad arguments" for some commands and nothing for others, and nothing outside the
process says which kind of command you just called.

Issue **#71**. This is the code half; the documentation half (§10.1's inventory of
who actually emits 2) closed in v0.2.2 and you are amending that note, not writing
it from scratch.

**Which side moves: the code.** The frozen table at `docs/LEDGER-CONTRACT.md`
(around `:692-707`) is **not edited**. 2 keeps meaning "bad arguments"; it merely
starts being produced. Amending §10 instead was considered and rejected: it would
freeze a distinction with no principle behind it (why should `tp init` separate a
typo from a failure and `tp task` not?) and leave the two tools consumers actually
wrap with no way to make that separation, forever.

Measured at the revision the issue was written against, from a throwaway consumer
repo:

```
tp bogus                          rc=2   tp task bogus                     rc=1
tp task claim (no id)             rc=1   tp task ready --phases (no value) rc=1 (bash unbound variable)
tp pump --bogus                   rc=1   tp pump bogusarg                  rc=1
tp pump --jobs (no value)         rc=1   tp pump --grain bogus             rc=1
tp init --bogus                   rc=2   tp cleanup --bogus                rc=2
tp monitor --bogus                rc=1   tp dag-render --bogus             rc=1
tp usage --bogus                  rc=1   tp stream-fmt --bogus             rc=0
```

`file:line` citations below were true at that revision. **Line numbers move** —
find each arm by its text, and if the code no longer says what is quoted, record
that in your completion note instead of editing by coordinate.

### The mechanical change, tool by tool

Add one helper beside the existing `die()` in each tool and call it **only** from
argument-parsing arms:

```sh
usage_die() { warn "$*"; exit 2; }   # bad CLI arguments (LEDGER-CONTRACT §10)
```

- **`libexec/tp-pump`** — `die()` is at `:329`. Call `usage_die` from the parser
  arms at `:339-381` (unknown flag `:379`, unexpected argument `:380`, the
  `--jobs` / `--usage-ceiling` / `--tick` / `--resume-max` range checks at
  `:344-363`), from the `--phases is required` check at `:387`, and from the grain
  validation at `:396-399`. **Leave `die()` = 1 for everything operational**,
  including the "tasks directory does not exist" refusal at `:393` — a missing
  workspace is not an argument error. G10.1 has just rewritten the `--jobs`
  validation to reject 0; route its refusal through `usage_die` rather than
  re-deriving it.
- **`libexec/tp-task`** — `die()` is at `:190-193`. Same helper; call it from the
  unknown-verb arm, from every `usage: tp-task <verb> …` arm, and from every
  unknown-flag arm. **Do not touch** `next`'s 1-for-empty-frontier, `scrub`/`fsck`'s
  3, or `resume-attempt`'s 10 — separate frozen rows, and moving them is MAJOR.
  The value-omitted flags that die as a bash `unbound variable` trace got a
  `need_val` guard in the v0.2.2 diagnostic patch; route that guard through
  `usage_die` so the two collapse into one call site rather than adding a second.
- **`libexec/tp-monitor:230` and `libexec/tp-dag-render:117`** — literally the same
  line twice: `*) echo "ERROR: unknown arg '$1'" >&2; exit 1 ;;`. Change the
  status only, on the unknown-arg arm only.
- **`gates/claude-usage:79,344`** — unknown-arg arms to 2. A gate's 10 (pause) and
  its operational failures are untouched; a gate whose *arguments* are wrong is
  not a pause.
- **`bin/tp`, `libexec/tp-init`, `libexec/tp-cleanup`, `libexec/tp-agent-watchdog`,
  `libexec/tp-disk-watchdog`** — already exit 2 for their own unknown arguments.
  They are in your footprint so you can verify that and keep them consistent (one
  shared message shape), not so you can rewrite them. If a tool has an
  argument-parsing arm still exiting 1, that is in scope; anything else there is
  not.
- **`libexec/tp-stream-fmt`** — do **not** simply make it exit 2. It is documented
  at `:4-5` as a pure stdin filter that takes no arguments, so there is no argument
  to reject, and it currently exits **0** for `--bogus`. Choose one and document
  the choice: give it a real `--help` plus an unknown-argument arm (then it exits 2
  like everything else, and `bin/tp:42`'s blanket promise that every command
  answers `tp <command> --help` becomes true), or delete that blanket promise. The
  promise is false either way today and must not survive this task. Prefer the
  first: `bin/tp:42` is a promise made to every consumer, and honouring it is
  cheaper than retracting it.

Two producers of 2 that are **not** yours and must keep working:
`runners/local/runner.sh:558-559` and `runners/claude-docker/runner.sh:383-384`
answer 2 for an unknown verb, and `docs/RUNNERS.md` §1.3's capability probe depends
on it. §10.2 records that meaning. Do not blur it: after this task, 2 means "bad
arguments" for every tool **and** "this runner does not implement that verb" for a
runner, and §10.1/§10.2 must both say so plainly enough that a consumer can tell
which it is holding.

### Documentation that stops being false

- **`docs/LEDGER-CONTRACT.md` §10.1** — the first divergence paragraph ("Neither
  `tp task` nor `tp pump` ever exits 2") becomes historical. Rewrite it to record
  the divergence as closed as of v0.3.0, with the exit-2 producer list now covering
  `tp task`, `tp pump`, `tp monitor`, `tp dag-render` and `tp usage`, and keep the
  v0.2.x statement clearly labelled for readers who cannot upgrade. Delete the
  "*What to key on instead:* … Parse stderr, or do not distinguish" advice — it is
  now wrong advice for v0.3.0 and it is the sentence integrators copied.
- **`docs/CLI-PUMP.md` §2.2 (`:175-200`)** — the row reading "Never (§2.2)" for
  exit 2 flips.
- **`docs/CLI-TASK.md`, `docs/CLI-TOOLS.md`** — exit-code tables.

### The migration note

Record it in §10.1 and in your completion note, verbatim, for G10.4 to lift into
CHANGELOG:

> **v0.3.0: `tp task` and `tp pump` now exit 2 for bad arguments (was 1).**
> Affected: unknown verb, unknown flag, a required value omitted, a value out of
> range, and `--phases` missing. Not affected: `tp task next`'s empty frontier
> (still 1), `scrub`/`fsck` violations (still 3), `resume-attempt`'s pause (still
> 10), and every operational failure (still 1).
> **If you wrote `if ! tp task …`, `|| handler`, or `set -e`, nothing changes** —
> the status is still non-zero. **If you wrote `[[ $? -eq 1 ]]` to mean "it
> failed", change it to `[[ $? -ne 0 ]]`**, or add 2 to the arm. If you were
> parsing stderr to tell a typo from a failure — which §10.1 told you to do
> against v0.2.x — key on the exit status instead and delete that parsing.

## Scope

Twenty-one paths, eleven of them executables. This is the widest footprint in the
range and it **blocks every sibling in its wave by construction**: it owns both
big tools, all seven peripheral tools, the gate, four docs and six suites. It is
scheduled here because here it blocks the fewest. The corollary is that you have
the file to yourself and no excuse for reaching outside it.

Do exactly one kind of change: the exit status of argument-parsing arms, plus the
documentation of that change. Do **not** take the opportunity to refactor an
argument parser, add a flag, change a message's wording beyond the status, or fix
an operational bug you notice. Do not touch `VERSION` or `CHANGELOG.md` — G10.4
owns them for this phase and the migration note reaches it through your completion
note.

Two files #71 names that are **not** in your `files:` list:
`tests/test-entrypoint.sh` and the two runners. The entrypoint suite's rc-1
assertion (around `:482`) is the entrypoint's own operator-misconfiguration exit,
not a `tp task` / `tp pump` usage error, so it should need no change — verify
that rather than assume it, and if it does need one, record it as debt instead of
editing the file.

Split point if your budget runs short: land `bin/tp` plus `tp-task` and `tp-pump`
with their suites and docs first, and release the task with the seven peripheral
tools recorded as the remainder. A half-swept tree is a worse contract than an
unswept one, so say precisely which tools are done in the note.
