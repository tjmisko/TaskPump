# G9.5 — No shipped default names one consumer's toolchain, terminal, remote or cache

## Spec

Two issues — #110 and #108 — and the residue of an extraction. Each item is a
default whose correct value belongs to the consumer or the host, and none of them
is behind a key. They are one task because they are the same class of edit and
because they land across five files that no other G9 task may hold at the same
time.

File:line citations come from the issue text. **Line numbers move**; grep for the
identifier beside each one. G9.2 has already passed over `libexec/tp-pump` and
G9.4 over `libexec/tp-monitor` and `libexec/tp-task` — read all three at HEAD.

### #110.a — `origin` is hardcoded, and the failure is swallowed

`tp task`'s push-retry rebases onto `origin/<branch>`
(`libexec/tp-task:393-395`) and the integration-trunk graduation pushes to
`origin` (`libexec/tp-pump:1814` — the only remote name in that file). A
repository whose remote is named anything else — `upstream`, `gh`, a fork
workflow — loses its push retry silently and its trunk push silently, because
both failures are discarded.

Ask git for the branch's configured upstream first
(`git rev-parse --abbrev-ref --symbolic-full-name @{u}`, or
`git config branch.<b>.remote`) and fall back to a new `TASKPUMP_REMOTE`,
default `origin`. **Stop discarding the push failure**: at minimum it is logged,
naming the remote and git's reason.

### #110.b — a Rust toolchain is on the shipped agent's PATH

`runners/claude-docker/entrypoint.sh:636`, inside `DEV_SESSION_SCRIPT`, does
`export PATH=/usr/local/cargo/bin:\$PATH`. The entrypoint is the generic,
project-neutral one, so a Node or Python consumer inherits a Rust path and has no
supported way to add its own. Put it behind `TASKPUMP_AGENT_PATH_PREPEND` and
drop the cargo literal from the shipped default — a Rust consumer sets the key.
`templates/` is already clean of toolchain names and is the standard to match.

### #110.c — the monitor spawns `wezterm`

`libexec/tp-monitor:1784` (`TASK_TERM="${TASKPUMP_MONITOR_TERM:-wezterm}"`) and
`:1789` (wezterm-specific argv) make "open this task in a terminal" dead on any
other desktop until the operator finds two keys that are not documented by
default. The correct pattern is in the same file at `:576`:
`EDITOR_BIN="${VISUAL:-${EDITOR:-nvim}}"`. Default `TASK_TERM` to `$TERMINAL`,
then a small probe list (`x-terminal-emulator`, `wezterm`, `kitty`, `alacritty`,
`gnome-terminal`), and **degrade with a message naming `TASKPUMP_MONITOR_TERM`**
when none is found, rather than failing silently.

### #110.d — the usage gate writes into its own install and shares one /tmp file

`gates/claude-usage:66-72`:

- `TASKPUMP_USAGE_RESET_FILE` defaults to a path inside the TaskPump
  *installation*, so on a read-only or root-owned install
  `tp usage --scan-logs` prints `reset backstop set` and then dies on the write
  under `set -e` — success announced, then abort. Default it to the state dir
  (`$STATE_DIR/.taskpump-usage-reset`), which is the value `libexec/tp-pump`
  already exports and therefore the value that is already correct under the pump.
- `TASKPUMP_USAGE_CACHE` defaults to a fixed `/tmp/claude-plan-usage.json`, so
  every user on a shared host reads and writes one another's plan-usage meter
  through a predictable path in a world-writable directory, and either of them
  can pre-create or replace it. Namespace it per uid
  (`${XDG_RUNTIME_DIR:-/tmp}/claude-plan-usage.$(id -u).json`), create it with
  restrictive permissions, and **refuse a pre-existing path the caller does not
  own** rather than trusting it.
- Guard the write (cited at `:302`) so a failure reports the path and the reason
  instead of aborting the scan after announcing success. The printed message and
  the exit status must agree.

### #108 — the pump demands `~/.claude` and `TASKPUMP_IMAGE` whatever runner is configured

TaskPump ships `runners/local`, whose header calls it "the runner that makes 'any
repository' true without a container runtime: no image to build, no daemon to
talk to, nothing to install". The supervisor checks its launch prerequisites
*before* the runner is ever consulted (`libexec/tp-pump:2879-2887`), so that
operator is first told to authenticate a product they are not using
(`no ~/.claude; run 'claude' to authenticate first`) and then, after satisfying
it with a `mkdir`, told to configure a container image for a runner that starts
no containers. The documented workaround is to set `TASKPUMP_IMAGE` to a lie.
Note the ordering in that block: the runner is validated *after* the two checks
that assume what the runner is.

Move both prerequisites behind the runner seam. The clean version — and the one
the plan's acceptance asks for — is an optional `preflight` verb on the runner
contract that the supervisor calls once at startup, whose non-zero exit carries
the runner's own reason. A runner without the verb is treated as passing, exactly
as `apl_runner_list_supported` already treats a missing `list` verb
(`libexec/tp-pump:2892-2897`). `runners/claude-docker` then checks `~/.claude`
and the image; `runners/local` checks `TASKPUMP_LOCAL_AGENT_CMD`.

Either way, `CLAUDE_DIR`'s refusal must name `TASKPUMP_AGENT_HOME` as the
override — today it names only `claude`, though the override exists at
`libexec/tp-pump:134`.

`docs/RUNNERS.md` §3.3 is honest that the prerequisites are container-shaped but
lists only two keys and closes with "Setting them is the whole adaptation." It is
not: the check the operator hits first is undocumented. That sentence must go.

  defaults of `TASKPUMP_USAGE_CACHE` and `TASKPUMP_USAGE_RESET_FILE`; README §6
  currently teaches `TASKPUMP_IMAGE=unused-…` as the way to run without

  new default, in your completion note** — that list is what G9.6 reconciles the

  not mention.

  You are in that file only for the remote.
