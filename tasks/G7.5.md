# G7.5 — The budget and the tripwires belong to the supervisor

## Spec

**Read this paragraph before anything else.** The whole unattended-safety milestone hangs
on this task. The plan's `safe_to_self_drain_after` field gives five reasons the operator
may not walk away before G7 is drained, and the first is this one: the supervisor has no
working bound on an agent that launches faithfully, burns turns, and lands nothing. Two of
`scrub`'s three tripwires never fire for any pump-launched agent, so `AGENTS.md`'s promise
that "if you do nothing at all, scrub eventually relabels the claim" is false today.
Unattended means precisely "nobody notices". This is the round the plan describes as
one-wide — nothing runs beside you, because everything after depends on the bound you land.

Two issues, and they are one mechanism seen from two ends: the runner resets the counters
every session, and the verb lets it. Line citations below are from the 2026-08-19 sweep and
have already moved once; at the time of writing `cmd_claim` is at `libexec/tp-task:869`,
`cmd_heartbeat` at `:945` and `cmd_scrub` at `:2102`. Search by name.

### #128 — the entrypoint re-claims the lead task before every session

`runners/claude-docker/entrypoint.sh` fires an unconditional "safety-net" `claim` before
each `claude -p` session, immediately followed by `heartbeat --start`, inside
`if [ -n '$TASK_ID' ]`. `SAFETY_TURNS` defaults to 3. `tp task claim` treats a same-branch
re-claim as an idempotent refresh and rewrites `turn_budget_remaining` back to the granted
value and `consecutive_failed_iterations` back to `0`. So the budget cycles 3 → 2 → 3 → 2
forever and the failure streak cycles 0 → 1 → 0 → 1 forever. Neither reaches its tripwire.
The third tripwire is re-armed by the same block's `heartbeat --start`, so it only fires if
the agent stops launching altogether — the one failure the pump can already see from
`docker ps`.

The A/B in the issue is the regression you must reproduce as a test. Five
`claim`/`hb --start`/`hb --end` cycles against a throwaway copy of
`tests/fixtures/generic-project`, agent commits nothing:

```
WITH the per-session claim:  budget=2 failures=1, every session, scrub silent, forever
CONTROL, claim issued once:  session 3 -> budget=0 failures=3, scrub: T2.1 -> needs-review
```

Three things make this worse than a missing guard. The codebase already diagnosed the exact
mechanism and did not generalise it — `libexec/tp-task`'s `resume_attempts` comment says
"`claim` also zeroes that counter on every (re)claim, so the pump's own resume cycle would
reset the very tripwire meant to stop it". Both shipped briefs already forbid the agent from
doing what the runner does, in as many words. And it defeats #61: the entrypoint already
fires `heartbeat --end`, so #61's acceptance can pass with both tripwires still dead.

The entrypoint half: read the task's `status` and `claimed_by` first — the file path and
`yq` invocation are already assembled two blocks down for the end-of-session check — and
skip the `claim` when it already reads `in_progress` claimed to `$CURRENT_BRANCH`. That is
exactly the check `templates/task-brief.md` tells the agent to perform. Keep
`heartbeat --start` unconditional; it is status-preserving and cheap.

### #90 — claim and heartbeat are self-service

`cmd_claim` writes `.turn_budget_remaining = $turns | .consecutive_failed_iterations = 0`
on every claim including the refresh path, so
`claim T1.1 --branch feat/g1-1 --turns 99999` took the budget from 40 to 99999 at rc=0.
`cmd_heartbeat` takes only an id and a mode; its sole guard is `status != in_progress`, so
`heartbeat T1.2 --start` from a caller that does not hold T1.2 returned rc=0 and moved
`last_heartbeat_ts` while `claimed_by` stayed `feat/g1-2` — the starvation half of the
claim-squatting problem made permanent.

A skeptic correction worth carrying: it is **not** true that every bound on a runaway lives
in the ledger. `reclaim_orphaned_claims` and `detect_stalled_orphans` key off live container
slugs plus `rev-list --count BASE_REF..branch` and read none of these fields, and
`resume_attempts` is not among the fields `cmd_claim` resets. The verified damage is exactly
the three scrub tripwires plus keeping a sibling's dead claim looking alive.

The durable half, in `libexec/tp-task`:

- A same-branch re-claim refreshes liveness. It stops writing `turn_budget_remaining` and
  `consecutive_failed_iterations` unless `--turns` was passed explicitly, and it never
  raises the budget above the first claim's grant — cap `--turns` at the recorded value, so
  the budget is monotonic non-increasing for the life of the claim. A refresh is not a
  fresh start.
- `cmd_heartbeat` requires `--branch` and refuses when it does not match `claimed_by`,
  leaving `last_heartbeat_ts` unchanged on refusal.
- `scrub` still parks a task whose budget is genuinely spent. The happy path is what the
  whole change exists to restore, so assert it rather than assuming it.

### The call sites G7.2 handed you

G7.2 landed the claimant checks on `complete`/`block`/`release` and the actor in the commit
trail, and deliberately did **not** update the call sites, because they are your files.
Land them now: `templates/task-brief.md` step 6 and `templates/phase-drain-brief.md` pass
`--branch`, and the entrypoint's safety-net `claim`/`heartbeat` calls pass `$CURRENT_BRANCH`
— they already have it in hand. Check G7.2's completion note for the exact signatures it
landed.

The briefs also need their framing fixed: both currently describe the claim as a one-time
launch event ("your first task may have been claimed and beaten for you at launch") when the
pump re-dispatches the same lead id on every resume. And `AGENTS.md`'s tripwire paragraph
asserts a scrub that cannot happen; after this task it can, and the text must say what a
refresh does and does not reset.
